# Experiment log

Everything measured in this project, with the setup needed to reproduce it.

Sections 1–5 ran on **CPU** (torch 2.14.0+cpu) — the CUDA-capable GPU on the
machine went unnoticed at first because the CPU-only torch wheel had been
installed, and `torch.cuda.is_available()` dutifully said False. Read those
wall-clock numbers as CPU numbers; comparisons between them are valid because
they share a machine. Section 6 onward runs on the GPU (RTX 5050 8 GB,
torch 2.14.0+cu130, bf16 autocast, fused AdamW).

Read the numbers as *relative* evidence about architecture choices, not as
absolute quality. These are 17M and 47M parameter models.

---

## The two presets

| | `nano_30b` | `nano_105b` |
| --- | --- | --- |
| attention | GQA, 6 q-heads / 2 kv-heads | MLA (`kv_lora_rank` 48) |
| layers | 8 | 12 |
| total params | 17.44 M | 47.39 M |
| active per token | 6.60 M (37.9%) | 13.33 M (28.1%) |
| experts | 16, top-2, +1 shared | 16, top-2, +1 shared |
| routing | `n_group=1` (ungrouped) | `n_group=4, topk_group=2` |
| RoPE | `theta=1e6`, no scaling | `theta=1e4`, YaRN-ready |

Both mirror their namesake's *ratios* (`moe_intermediate_size` = hidden/4 vs
hidden/2, dense FFN = 2× vs 4× hidden), not just the name. Sparsity is milder
than the originals: 16 experts top-2 is 12.5%, where the real models run 6/128
and 8/128 (~5%). Top-1 at this scale would be degenerate.

Parameter counts were derived analytically before the code ran and match
`model.num_params()` exactly.

## 1. English (tinyshakespeare, 1.12 MB)

`--block-size 256 --batch-size 16`, identical seed and data order.

| | GQA, 1000 steps | GQA, 600 steps | MLA, 600 steps |
| --- | --- | --- | --- |
| **val loss** | **1.5190** | 1.5701 | 1.5467 |
| bits/byte | 2.192 | 2.265 | 2.231 |
| wall clock | 1345 s | **921 s** | 1781 s |
| throughput | 3000 tok/s | 2692 tok/s | 1393 tok/s |
| imbalance peak → final | 5.19× → 1.16× | 3.35× → 1.18× | 7.02× → **1.13×** |

**At matched steps (600), MLA wins** — 1.5467 vs 1.5701, worth 0.034 bits/byte.
It should: 2× the active parameters.

**At matched wall clock, GQA wins outright.** The 1000-step GQA run reaches a
*better* loss (1.5190) in *less* time (1345 s) than MLA needs for 1.5467. Two
extra active parameters bought 0.023 nats per step and cost 1.9× the time per
step.

A first comparison at 1000 vs 600 steps was confounded by differing cosine
schedules — at step 350 the longer run was still at lr 2.52e-4 while the shorter
had decayed to 1.65e-4. The 600-step GQA run above was added specifically to
remove that. Steps 0 and 100 are bit-identical across the two GQA runs
(warmup overlaps), confirming determinism.

## 2. Hindi

Corpus from `fetch_hindi.py`, which streams the Hindi Wikipedia bz2 dump and
stops early — **12.59 MB of clean prose from 3.1 MB downloaded (1% of the
240 MB dump)**, 450 articles, 73.8% Devanagari. The API route was abandoned:
Wikipedia returns HTTP 429 within a few requests.

`--block-size 512 --batch-size 8`. The doubled block size is deliberate: Hindi
runs at **2.48 bytes per character**, so a 256-byte window is only ~103
Devanagari characters — barely a sentence. Same tokens per step, twice the
linguistic context.

| | GQA 1000 | MLA 1000 | **GQA 2000** |
| --- | --- | --- | --- |
| **val loss** | 0.7373 | 0.7450 | **0.6734** |
| bits/byte | 1.064 | 1.075 | **0.972** |
| bits/char | 2.64 | 2.67 | **2.41** |
| wall clock | 1859 s | 3221 s | 3345 s |
| imbalance peak → final | 7.80× → 1.25× | 5.41× → 1.34× | → 1.23× |

**MLA's per-step advantage did not survive the language change.** It won by
0.034 bits/byte on Shakespeare and *loses* by 0.011 on Hindi, with 2× the active
parameters and 1.7× the wall clock. Most likely neither model is
capacity-limited here: 1000 steps covers 4.1M tokens of an 11.3M-token split, so
extra parameters have nothing to bite on. tinyshakespeare's 1 MB was small
enough that the bigger model's fit mattered.

**Group-limited routing damped rather than amplified collapse.** Prediction
going in was that Devanagari's clustered byte statistics would make the 105B's
group constraint collapse harder. It started *better* balanced (5.41× vs 7.80×)
and merely converged more slowly. Wrong prediction, recorded as such.

**Doubling steps bought 0.092 bits/byte** (1.064 → 0.972), inside the 0.05–0.12
predicted from log-linear scaling, and crossed below 1 bit/byte. Mid-run eval at
step 999 of the 2000-step run was 0.7450 — essentially identical to the
1000-step run's final 0.7373 despite a 6× higher LR at that moment — so the gain
came from the extra steps plus the anneal, not a lucky schedule.

### The tokenizer cost, measured

A byte-level model on Hindi pays 2.48 tokens per character where English pays 1.
The trained model learned UTF-8 unaided: over 1512 generated bytes, **zero
decode errors**, 79.1% Devanagari (corpus 73.8%), 2.58 bytes/char (corpus 2.48).
It inferred that Devanagari costs three bytes and which continuation bytes are
legal, purely from byte statistics, before learning any Hindi.

**bits/byte is misleading across scripts:**

| | bits/byte | bytes/char | **bits/char** |
| --- | --- | --- | --- |
| Hindi | 0.972 | 2.48 | **2.41** |
| English | 2.192 | 1.00 | **2.19** |

Hindi looks twice as good per byte, but UTF-8 continuation bytes are nearly free
to predict and drag the average down. Per character Hindi is *harder*. Always
report bits/char when comparing across scripts.

This is the fertility argument made concrete: every Devanagari character costs
2.48 positions of context, KV cache and latency. Sarvam's tokenizer reports
1.4–2.1 tokens *per word*; bytes are ~15–20 per word.

## 3. Does YaRN earn its place?

Both Shakespeare checkpoints were trained at `block_size=256` with plain RoPE.
Evaluated at 2× and 4× that, either naively or with the rotary rebuilt for YaRN
(`factor = length/256`). Same weights, **zero fine-tuning**.
Reproduce with `python eval_context.py --ckpt ckpt_105b.pt`.

Loss by position inside a 1024-byte window:

| positions | `105b` naive | `105b` YaRN | `30b` naive | `30b` YaRN |
| --- | --- | --- | --- | --- |
| 0–256 *(in-distribution)* | **1.5421** | 1.6802 | **1.5076** | 1.6808 |
| 256–512 | 1.7924 | **1.6989** | **1.6046** | 1.7052 |
| 512–768 | 2.8697 | **1.7034** | **1.6861** | 1.6898 |
| 768–1024 | 3.0342 | **1.7131** | 1.8616 | **1.6882** |

**For the MLA preset YaRN is the difference between working and not.** Naive
extension collapses 1.54 → 3.03 as you walk out the window. With YaRN the curve
is nearly flat, 1.68 → 1.71 across a 4× extension.

**For the GQA preset YaRN is a net loss — but a close one.** `rope_theta=1e6`
already extrapolates gently (1.51 → 1.86), so there is less for YaRN to repair,
and on average the repair does not pay for itself: +0.0589 at 512, +0.0260 at
1024. What it buys is the same flat curve the MLA preset gets — it never leaves
1.68–1.71 across the window — so it ties in the third quarter (1.6898 vs 1.6861)
and wins
outright in the fourth (1.6882 vs 1.8616).

**YaRN's price is visible in both**: at 0–256 it is *worse* than naive (1.68 vs
1.54; 1.68 vs 1.51). You trade accuracy on the range you trained for against not
falling apart beyond it. A single averaged number hides this entirely — the
position-bucketed view is what exposes it.

**Correction.** The GQA column was regenerated after a fix. `GQAttention` set
`scale = head_dim**-0.5` and never applied YaRN's logit-temperature term
(`mscale**2`, 1.296 at factor 4), which `MLAttention` had carried since it was
written — so the earlier GQA row measured the band blend alone while the prose
credited both halves, and quoted 1.874×, which is `mscale**2` at the real 105B's
factor 40, not at the factor 4 measured here. With the term applied, YaRN's far-end
win on GQA roughly doubles (1.6882 vs the previous 1.7854, against naive 1.8616)
and its in-distribution cost grows (1.6808 vs 1.6482). The verdict does not change.
The MLA columns are untouched by the fix and reproduce to the fourth decimal,
which is what says the harness itself is stable.

The two presets independently reproduce **why Sarvam chose oppositely**: 30B at
`rope_theta=8e6` with `rope_scaling: null`, 105B at `rope_theta=1e4` with YaRN
factor 40. Each strategy wins on its own model.

## 4. MoE dispatch: `sparse` vs `dense`

| | eager, `nano_30b` | eager, `nano_105b` | Dynamo | equivalence |
| --- | --- | --- | --- | --- |
| `sparse` (default) | **574 ms/step** | **1407 ms/step** | 9 graphs, 8 breaks | — |
| `dense` | 1350 ms/step | 2955 ms/step | **1 graph, 0 breaks** | bit-identical |

Sparse dispatch uses `nonzero`, whose output shape is data-dependent, so Dynamo
cannot capture it. Setting `capture_dynamic_output_shape_ops` does not help, and
neither does removing the `if sel.numel() == 0` guard — both were tested.
`dense` runs every expert on every token and combines through a one-hot weight
matrix: static shapes, `num_experts/top_k` times the expert FLOPs.

Sparse stays the default (it is what a real MoE does, and it wins in eager); use
`--moe-impl dense` when you want `--compile` to mean something. Graph-break
counts are asserted in tests **in both directions**, so if a future torch stops
breaking on `nonzero` the test fails rather than the docs silently rotting.

## 5. Load balancing behaviour

The aux-loss-free bias is the one mechanism the released inference code shows
being *consumed* but never *written* — it is training-time only. Findings from
implementing it:

- **Imbalance rises before it falls, in every run.** At `rate=1e-3` the bias
  moves ±0.05 in 50 steps against sigmoid scores spanning (0,1), so the router
  collapses toward favourites faster than the correction pushes back. Past
  ~step 100 the accumulated bias overtakes it. Peaks observed: 5.19×, 7.02×,
  7.80×, 5.41×; finals: 1.13×–1.34×. **Do not read the early climb as a broken
  balancer.**
- **The rule oscillates and never settles.** `sign()` applies a full-size step
  however small the error. Measured ping-pong: 1.188× ↔ 1.734×, period 2, at
  `rate=0.05` on a frozen batch. Inherent to DeepSeek-V3's rule; harmless in
  real training where the rate is 50× smaller and batch variation averages it.
- **Recovery time is arithmetic.** An overloaded expert's bias falls by `rate`
  while a starved one rises by `rate`, so a skew of `S` closes at `2·rate` per
  step and needs **~`S/(2·rate)` steps** before routing can change at all.
  Measured: skew 3.0 at rate 0.01 shows *zero* movement in 120 steps. Check the
  budget before raising `bias_update_rate` because imbalance looks stuck.

## 6. Scaling to the GPU: sizing `nano_350m`

Target was "500M on the 8 GB RTX 5050". The arithmetic said Muon would make
443M fit; the measurement said otherwise. All rows: batch 8 × block 512, bf16
autocast, gradient checkpointing on unless stated.

| total params | optimizer | ms/step | tok/s | peak GB | verdict |
| --- | --- | --- | --- | --- | --- |
| 443M | AdamW, no ckpt | 31573 | 130 | 15.75 | WDDM spill, thrashing |
| 443M | AdamW | 2716 | 1508 | 9.74 | still spills |
| 443M | Muon | 6997 | 585 | 7.99 | fits, but 2.6× slower |
| **353M** | **AdamW** | **827** | **4955** | **6.34** | **the preset** |
| 281M | AdamW | 696 | 5887 | 5.15 | headroom |

Two findings worth keeping:

- **Windows WDDM hides OOM.** Exceeding VRAM spills to system RAM instead of
  raising an error — the 443M/no-ckpt row "works" at 12× slowdown. On Linux
  those rows would crash, which is kinder.
- **Muon is the wrong tool for fine-grained MoE on one small GPU.** It converges
  faster per step (3.12 vs 3.50 at step 19 of a smoke run) and stores one
  momentum buffer instead of AdamW's two moments (12 vs 16 bytes/param) — but
  Newton–Schulz runs per-tensor, and this model has 383 small 2D matrices
  (12 experts × 3 matrices × 19 layers + attention), so launch overhead makes it
  **2.6× slower per step**. Muon's wins come on dense models with few large
  matrices; use `--optimizer muon` here only when memory, not time, is the
  constraint. Implementation in `muon.py`.

Final preset: `nano_350m` — 353M total / 152M active, 20 layers, hidden 1024,
12 experts top-3 + 1 shared, GQA 16q/4kv, `rope_theta 1e6`. Requires
`--grad-ckpt` (15.75 GB without, 6.34 GB with).

20× the parameters and 8.6× the data bought **0.11 bits/byte** (0.27

## 7. The tokenizer experiment: bytes vs BPE at matched compute

The largest single result in this log. `bpe.py` is a from-scratch byte-level
BPE (stdlib only): 16,384-token vocab trained on the 12.6 MB corpus in **10
seconds** (unique-chunk weighting + incremental pair counts + lazy max-heap),
exact roundtrip by construction, byte fallback for unseen scripts.

Fertility, measured on the held-out 107 MB corpus:

| tokenizer | bytes/token | tokens/word | text in a 512-token window |
| --- | --- | --- | --- |
| bytes | 1.00 | ~15–20 | ~206 Devanagari chars |
| **hi16k BPE** | **9.64** | **1.34** | **~2,000 chars** |

1.34 tokens/word sits inside the 1.4–2.1 Sarvam reports for their 262k-token,
22-language tokenizer — achievable monolingually with 16k tokens and 10 seconds
of training. Then two runs differing **only in tokenizer**: same 353M trunk
(the BPE model is 386M total — the extra 33M is the bigger embedding+head),
6000 steps, batch 8 × 512, same schedule, same GPU.

| | byte `ckpt_hindi_350m` | **BPE `ckpt_hindi_bpe`** |
| --- | --- | --- |
| vocab | 259 | 16,384 |
| val loss (nats/token) | 0.5975 | 4.6795 |
| **bits/byte** | 0.862 | **0.700** |
| bits/char | 2.14 | **1.74** |
| text seen per step | ~4 KB | **~39 KB** |
| corpus epochs | 0.25 | 2.4 |
| wall clock | 93 min | 100 min |

Raw losses are incomparable across vocabularies (0.60 vs 4.68 — predicting one
of 16,384 is a harder per-token task than one of 259); bits/byte is the honest
axis, and the `.bin` metadata carries the conversion. **The tokenizer bought
0.162 bits/byte at identical compute — more than the 20× parameter scale-up
bought (0.110)**. Mechanism: every training step witnessed 9.64× more Hindi.

Two caveats, stated rather than hidden. The BPE run cycled its corpus 2.4×
where the byte run never repeated — that asymmetry is inherent to the
comparison (a tokenizer compresses the corpus too), and val loss was still
falling at the end (0.717 → 0.700 over the last 1500 steps), so repetition had
not begun to bite. And the byte model gets one structural consolation: it can
never emit an out-of-vocabulary word, while the BPE model's rare-word tail is
thinner.

Sample quality moved more than either loss number. The BPE model produces
paragraph-length, topic-coherent Wikipedia-register Hindi — a Mumbai prompt
yields a sustained tourism description across eight sentences — where the byte
353M managed correct single sentences and the 17M managed fragments. Still
factually unreliable (invented capitals, "पाकिस्तान और पाकिस्तान के बीच"), and
it inherits the corpus's `ref` leakage verbatim.

Generation is also ~9.6× cheaper per character: 120 generated tokens now yield
~1,150 bytes of text where the byte model needed ~1,200 tokens for the same.

All four Hindi models:

| | params | tokenizer | device | **bits/byte** | bits/char |
| --- | --- | --- | --- | --- | --- |
| `ckpt_hindi_2k` | 17M | bytes | CPU | 0.972 | 2.41 |
| `ckpt_hindi_105b` | 47M | bytes | CPU | 1.075* | 2.67* |
| `ckpt_hindi_350m` | 353M | bytes | GPU | 0.862 | 2.14 |
| **`ckpt_hindi_bpe`** | **386M** | **hi16k** | **GPU** | **0.700** | **1.74** |

*\*1000 steps, not directly comparable to the 2000/6000-step rows.*

## 8. Corpus cleaning: v2

The v1 BPE model had *learned the corpus's markup leakage as a genre feature* —
`ref name=` fragments mid-sentence, and one prompt (क्रिकेट) collapsing entirely
into hallucinated `gallery`/`File:` blocks. Two fixes in `fetch_hindi.py`:
entity-decode **before** tag-stripping (the dump stores tags as `&lt;ref&gt;`,
so v1 stripped tags first and left the unmasked text behind), and `--keep-prob`
sampling across the **whole** dump instead of taking the front 11% (which had
monuments but hardly any cricket).

v2 corpus: 192.4 MB from 100% of the dump at keep-prob 0.3. Per MB:
`ref name` 116.7 → **0.01**, `ref /ref` 182.7 → **0.00**, `.jpg` 19.4 → 2.6;
क्रिकेट mentions 2.4×. Tokenizer retrained on the clean text improved slightly
(1.30 tok/word, 9.79 B/tok). Same 6000-step recipe, ~1.25 epochs.

**Fair comparison requires shared text** — each run's own val split is different
text, so own-val numbers (0.700 dirty, 0.631 clean) don't compare. On an
identical 3.8 MB held-out slice, each model using its own tokenizer:

| | bits/byte on shared text |
| --- | --- |
| v1 (dirty corpus) | 0.6631 |
| **v2 (clean corpus)** | **0.6087** |

**Cleaning bought 0.054 bits/byte** at identical compute — about half what the
tokenizer bought, and for ~30 minutes of scrubber work.

Qualitatively: the v1 failure modes are gone (no `ref` fragments anywhere; the
क्रिकेट prompt now degrades gracefully into prose instead of file-markup) — but
cleaning is whack-a-mole, and removing the dominant artifact promoted the
next ones. v2 samples surface **numeric citation brackets** (`[3] [5] [1]`,
present in the source text and untouched by the scrubber, likely unmasked by the
same entity decoding) and occasional English pseudo-title runs from the broader
article mix. Also spotted: `----` (wikitext horizontal rule) survives. Each is a
one-line scrubber fix for the next data pass; the lesson worth keeping is that
**the model is a magnifying glass for whatever is left in the data** — 0.01% 
contamination is invisible in loss and visible in generation.

Operational note: the run was interrupted twice and recovered both times via
`--resume`. The second recovery exposed a real bug — the resume path loaded the
4.6 GB optimizer checkpoint onto the GPU with `map_location=args.device` and
kept it referenced for the life of the run, forcing permanent WDDM spill
(210 tok/s instead of ~4,400, GPU at 24 W). Fix: load to CPU, let
`Optimizer.load_state_dict` place states, `del` the blob. A kill mid-`torch.save`
also truncated the best-val file once; the `.last` file restored it. Both
behaviours are why the two-file checkpoint scheme exists.

## 9. The v4 recipe, A/B at matched compute, on a shared benchmark

Hardware note: sections 6–8 ran on an RTX 5050 8 GB; the machine now carries an
**RTX 5070 Ti 16 GB** (torch 2.11.0+cu128). Wall-clock numbers here are not
comparable to earlier sections; everything else is.

### The benchmark

Own-val numbers cannot be compared across corpora or tokenizers (§8). So:
`make_bench.py` builds one fixed held-out file from a *differently seeded*
sample of the dump (`--seed 2024 --keep-prob 0.05`) and drops every document
whose Devanagari-only signature (three 80-letter windows) appears in **any**
corpus a checkpoint here trained on. The first cut used a plain 200-character
substring probe, which missed articles the v1 scrubber had mangled — and
`ckpt_hindi_bpe` (v1 corpus) scored 0.637 bits/byte on it, "best of all".
With the script-only signature that number is 0.734, worst of the BPE models.
**A benchmark leak of 11% of documents moved a model by 0.1 bits/byte**;
1,225 of 2,572 candidate documents had to go. Final file: 1,347 docs,
13.61 MB, 5.41 M chars. `eval_bench.py` scores in non-overlapping
`block_size` windows, plain `encode` (no EOS, so older models are not
penalised), each checkpoint with its own tokenizer.

### The A/B

Same trunk (`nano_350m`, 386M with the 16k head), same corpus *text*
(`hindi_v4.txt`, 194 MB, 21,897 articles with titles), same tokenizer
(`hi16k_v4`), same seed, 6000 steps × 8 × 512, lr 6e-4, `--grad-ckpt`,
`--moe-impl grouped`, bf16.

| | A: old recipe | **B: v4 recipe** |
| --- | --- | --- |
| document boundaries | none (articles run together) | EOS after every article |
| sampling | with replacement (random offsets) | `WindowSampler`, no replacement, 1.41 epochs |
| router regularisers | — | seq-balance 1e-4, z-loss 1e-3 |
| own val (nats/token) | 4.5606 | **4.3728** |
| final imbalance | 1.46× | **1.27×** |
| throughput | 11.8k tok/s | 11.0k tok/s (the regularisers cost ~7%) |
| wall clock | 2080 s | 2241 s |
| **benchmark bits/byte** | 0.6878 | **0.6655** |
| benchmark bits/char | 1.7309 | **1.6747** |

**−0.022 bits/byte at identical compute on identical text, scored without
EOS** (so B gets no credit for the boundary tokens it learned). For scale:
the tokenizer bought 0.162, cleaning 0.054, 20× parameters 0.110. This is a
recipe change, not a data change, and it lands at ~40% of what cleaning did.

Own-val is *not* the fair axis here — B's split contains EOS tokens and
document starts (the first tokens after an EOS are near-unpredictable, which is
why B's *training* loss reads 0.4–0.5 higher than A's all run while its val
reads lower). The benchmark is.

### Dispatch and decoding, same session

`--moe-impl grouped` vs `sparse` on this trunk, 40-step probes: **11.9k vs
8.0k tok/s** (1.48×), and 328 ms/step flat against 330–560 ms jittering —
`sparse` does a `nonzero` and a `.numel()` per expert per layer, a device sync
each. Decoding `ckpt_hindi_v3`, 300 tokens, batch 1: sparse 16 tok/s with or
without the KV cache; grouped 21 uncached → 28 cached → **33** with the
expert stack cached in eval mode. ~1,000 kernel launches per token is the
ceiling on this machine (no host compiler for Inductor or CUDA graphs), and
it is a serving problem, not a model problem.

## 10. Architecture ablations on the v4 recipe

Five runs, everything identical to §9's run B except one `--cfg` override
each, at a **2000-step** budget (a third of §9's), scored on the shared
benchmark. Directions at 2000 steps are usually the directions at 6000;
magnitudes are not, so read the deltas as rankings.

| | params (total / active) | own val | **bench bits/byte** | Δ vs baseline | wall |
| --- | --- | --- | --- | --- | --- |
| baseline (12×384, top-3, +1 shared) | 386M / 185M | 5.2973 | 0.7970 | — | 770 s |
| no shared expert | 364M / 163M | 5.2773 | 0.7937 | **−0.0033** | 779 s |
| fine-grained 24×192, top-6 | 375M / 185M | **5.2415** | **0.7891** | **−0.0079** | 1209 s |
| top-2 instead of top-3 | 386M / 163M | 5.2812 | 0.7941 | −0.0029 | 1099 s |
| sliding window 256 on layers 0–9 | 386M / 185M | 5.2803 | 0.7953 | −0.0017 | 894 s |

Every ablation beat the baseline, which says the preset is mis-tuned rather
than that any single idea is magic. Three of them beat it with *fewer*
active parameters (no shared expert, top-2) or the same (window), so the
"loss vs FLOPs" story is better than the table looks:

- **Fine-grained experts win outright** — same active FLOPs, −0.008
  bits/byte, the largest single move here. Which is DeepSeek-V3's argument
  (many small experts, higher combinatorial capacity) reproduced at 386M. The
  price is launch count: 24 experts is twice the kernels per layer, 1.57× the
  wall clock in this launch-bound regime, and on a compiled stack that tax
  mostly disappears.
- **The shared expert is not earning its 22M parameters** at this scale on
  this data. Drop it and the model gets *better*. Sarvam keeps one in both
  real models; at 128 experts and 4T tokens the trade may differ.
- **Top-2 ≥ top-3**: 12% fewer active parameters, slightly better loss. The
  aux-loss-free balancer keeps top-2 at 1.3× imbalance without trouble.
- **Windowing half the layers is free** on 512-token training, as it should
  be — a 256 window at block 512 removes almost nothing a layer-0 head wants —
  and it is the cheapest KV cache reduction available. It needs a long-context
  eval (`eval_context.py`) to say anything about what it costs beyond 512.

Wall-clock varies ±20% run to run on this box (WDDM, background load); the
kernel-count argument for fine-grained experts is sound, the exact ratio is not.

A combined preset — 24×192 experts, top-4, no shared expert, window on the
lower half — is the obvious next run; it was not made here because each
ablation was run against the baseline alone, and interactions are exactly what
that design cannot see.

## 11. The data lever: the whole dump at the same compute

`fetch_hindi.py --keep-prob 1.0` on the full dump: 72,467 articles, 648 MB.
Every benchmark article removed by title (1,347) plus 47 near-duplicates by
signature, leaving **633.7 MB, 71,073 documents, 62.9M tokens** with a
tokenizer trained on it (`hi16k_full`, 10.07 B/tok). Then §9's run B exactly
— same 6000 × 8 × 512, same recipe — so the only change is 3.3× the unique
text: **0.43 epochs instead of 1.41**.

| | `ckpt_hindi_v4` | **`ckpt_hindi_full`** |
| --- | --- | --- |
| unique tokens / epochs | 19.1M / 1.41 | 62.9M / 0.43 |
| own val (own split) | 4.3728 | 4.3259 |
| **bench bits/byte** | 0.6655 | **0.6586** |
| bench bits/char | 1.6747 | **1.6572** |
| wall clock | 2241 s | 2855 s |

**−0.007 bits/byte.** Real, and small — a third of the recipe change, a
seventh of the tokenizer. This is what the repetition literature predicts:
below ~4 epochs, repeated data is nearly as good as fresh data, so a corpus
that was only being cycled 1.4× had little to gain from not being cycled. The
model is compute-bound at this budget, not data-bound. More data starts
paying when steps go up with it; at 6000 steps the 62.9M tokens are 57%
unseen.

The sample (`मुंबई\n\n`, 34 tokens, stopped at EOS) came out as a stub —
a heading and a list of road and airport names — which the full dump has far
more of than the 30% sample the earlier runs saw (the sampled corpora and this
one share the 600-character floor, but the tail of short list-like articles is
long). One draw at temperature 0.8 is not evidence; it is a reminder that
"more data" changed the *mix*, and a corpus filter on prose density would be
the next data-side lever.

## 12. The ablation winners together

`--cfg num_experts=24 moe_intermediate_size=192 num_experts_per_tok=4
num_shared_experts=0 sliding_window=256 max_window_layers=10`, v4 recipe on
the full corpus, 6000 steps — §11's `ckpt_hindi_full` is the control.

| | `ckpt_hindi_full` | **`ckpt_hindi_combo`** |
| --- | --- | --- |
| experts | 12×384, top-3, +1 shared | 24×192, top-4, no shared, window 256 on 10/20 layers |
| params total / **active** | 386M / 185M | 364M / **140M** (−24%) |
| own val (same split) | **4.3259** | 4.3334 |
| bench bits/byte | **0.6586** | 0.6595 |
| final imbalance | 1.42× | 1.76× |
| wall clock | 2855 s | **2426 s** (−15%) |

**Same loss, three-quarters of the active compute.** The three ablations that
each won at 2000 steps did not add up to a lower loss at 6000; they added up
to a *cheaper* model at the same loss — +0.001 bits/byte, inside the noise,
for 24% fewer active parameters and 15% less wall clock even with twice the
expert launches. Two readings, both probably true: at 2000 steps the wins
were partly "learns faster early", which a 3× longer schedule erases; and
top-4 of 24 (17%) is a coarser selection than top-6 of 24 (25%), so some of
the fine-grained gain was spent buying the FLOP cut.

Balancing got harder: 24 experts finish at 1.76× against 1.42× — the bias
rule has twice the slots to equalise with the same step size. Raising
`bias_update_rate` for fine-grained configs is the obvious knob, untested.

Samples (`--seed 7`, 200 tokens):

- `मुंबई\n\n` — a "how to reach" section: सड़क मार्ग / हवाई मार्ग paragraphs
  about highways and stations, fluent and repetitive, never stopping.
- `भारतीय क्रिकेट टीम\n\n` — two clean sentences (appointed captain, added to
  the team on 7 December 2019) and EOS at 23 tokens.
- `हिन्दी साहित्य\n\n` — one sentence, then an award list: साहित्य अकादमी
  पुरस्कार −2012, −2002, −2009 … EOS after 186 tokens.

Two of three drift into the list register within a paragraph. That is the
corpus, not the architecture — hence §13.

## 13. Prose filtering: a clean negative

`filter_prose.py` on the full corpus — drop lines under 40 characters that do
not end a sentence, then drop articles with under 40% sentence-ended lines —
keeps 89% of the bytes (63,017 of 71,073 documents, 54.7M tokens with the
same `hi16k_full` tokenizer). Same recipe and budget as `ckpt_hindi_full`.

| | `ckpt_hindi_full` | `ckpt_hindi_prose` |
| --- | --- | --- |
| tokens / epochs | 62.9M / 0.43 | 54.7M / 0.50 |
| own val | 4.3259 | 4.3278 (different split) |
| Wikipedia bench bits/byte | **0.6586** | 0.6818 |
| Wikisource bench bits/byte | **0.8947** | 0.9172 |

**Worse on both, by 0.023.** The Wikipedia loss was predictable — the
benchmark is unfiltered, a quarter of it list-shaped, and the model never saw
a list — but the literature benchmark is pure prose and the prose model loses
there too. So the lines the filter removed were carrying signal: headings and
list items are where names, dates and entity types cluster, and a model that
has seen fewer of them predicts them worse *in running prose as well*. The
samples did come out prose-shaped (a film-release paragraph for `मुंबई`, two
clean sentences and EOS for the cricket prompt) — the filter fixed the
generation register and paid for it in loss. That is a real trade, but it is
not the one the section-11 sample implied: the model's list habit is learned
from data that is also teaching it Hindi.

## 15. What the sliding window costs past the training length

`eval_context.py --device cuda` on the two 2000-step ablations — the baseline
and the window-256-on-layers-0–9 model — at 1×, 2× and 4× the 512-token
training length, naive and with YaRN (`factor = length/512`):

| context | baseline naive | baseline YaRN | window naive | window YaRN |
| --- | --- | --- | --- | --- |
| 512 (trained) | 5.2782 | — | 5.2656 | — |
| 1024 | 5.3835 | 5.3693 | **5.3596** | **5.3554** |
| 2048 | 5.4428 | 5.3593 | **5.3746** | **5.3466** |

| positions in a 2048 window | baseline naive | window naive | baseline YaRN | window YaRN |
| --- | --- | --- | --- | --- |

quality; the §12 preset was right to keep it.

## 16. `bias_update_rate` for fine-grained experts

§12 flagged that 24 experts finish at 1.76× imbalance against 12 experts'
1.42×. Three rates on the combo preset, full corpus, 2000 steps each:

| rate | own val | bench bits/byte | imbalance, mean of last 10 logs | range |
| --- | --- | --- | --- | --- |
| 1e-3 (default) | 5.2348 | 0.7885 | 1.90× | 1.58–4.88× |
| **3e-3** | 5.2282 | **0.7870** | 1.88× | 1.58–4.64× |
| 1e-2 | 5.2279 | 0.7870 | 2.59× | 2.02–4.47× |

**The imbalance is not costing loss.** Tripling the rate buys 0.0015
bits/byte and moves the balance by nothing measurable; ten× buys the same
0.0015 and makes the balance *worse* on average (2.59×), because a `sign()`
step of 0.01 against sigmoid scores in (0, 1) overshoots and the rule
ping-pongs — §5's oscillation, now visible at training scale. The 1.7–1.9×
floor at 24 experts is what a fixed-step balancer settles to with twice the
slots per token; a smaller model on more data has enough spare capacity that
the imbalance is paid for in routing, not in perplexity. 3e-3 is marginally
the right default for the fine-grained preset; the difference is inside the
run-to-run noise of §10.

## 17. Closing the register gap: Wikisource as training data

§14 found a flat 0.24 bits/byte gap between Wikipedia and literature for every
model, and said it was a corpus problem. Test: the whole Hindi Wikisource dump
(154,843 scanned book pages, **689 MB — larger than Hindi Wikipedia**), the
1,426 benchmark pages removed by exact title, interleaved document-by-document
with the full Wikipedia corpus so the val split is mixed too. New tokenizer
(`hi16k_mixed`, 9.41 bytes/token — the older orthography costs a little
fertility). Combo preset, same 6000-step budget: **140.6M tokens, 0.17
epochs**, half of them Wikipedia.

| | `ckpt_hindi_combo` (Wikipedia only) | **`ckpt_hindi_mixed`** |
| --- | --- | --- |
| Wikipedia bench | **0.6595** | 0.7068 (+0.047) |
| Wikisource bench | 0.8970 | **0.7660 (−0.131)** |
| register gap | 0.238 | **0.059** |
| mean of the two | 0.778 | **0.736** |
| final imbalance | 1.76× | 1.56× |

**The gap is three-quarters closed, for a fifth of it back on Wikipedia.**
Half the Wikipedia tokens cost 0.047 there; the literature the model had never
seen is worth 0.131 where it matters. Averaged over both registers it is the
best model in the log by 0.042 — more than the recipe change and the data
lever together — and it is the first result here that is not a refinement of
"train on Wikipedia better".

The samples switch register by prompt. `मुंबई\n\n` becomes a political
biography (born 15 May 1927, Congress, chief minister of Delhi, then of Uttar
Pradesh — all invented, all in the encyclopaedic voice). `उसने कहा\n\n` — "he
said" — becomes first-person narrative and *stops at EOS*: "मैं ऐसा ही करना
चाहता हूँ कि मैं भी इस विश्वासके कारण …", with Wikisource's pre-1950s
orthography intact (विश्वासके, बारेमें, उद्देश्यको — postpositions joined to
the noun). It learned the register and its spelling conventions from 0.17
epochs, which says how little of the Wikisource text it needed.

The cost side is real and should not be waved away: a Wikipedia-only
deployment would take the 0.047. But nothing a user asks a Hindi model is
Wikipedia-shaped, and the 0.24 gap was the number that said so.

## 19. Accuracy: a golden set

Everything above is compression. bits/byte says how well a model predicts
held-out text; it never says whether the model gets anything *right*, and
the samples make clear that fluency and correctness have come apart — every
date, population and captaincy in §9–18's samples is invented. So, the first
accuracy axis: `make_golden.py` builds **600 Hindi cloze items** from the two
benchmark files (no checkpoint trained on either), one per document, and
`eval_golden.py` scores them. An item is a prose prefix of up to 120 words,
ending on the word before a blank, and the gold answer is the content word
that actually follows. Items are filtered to real sentences — the line must
have ten or more words, end on a sentence mark, and carry under 10% digits;
documents must be at least half sentence-ended lines and not Marathi, which
shares the script and turned up in the first draft as a list of plays. Four
cells of 150: Wikipedia and Wikisource, each split into

- **in_context** — the gold word already occurred earlier in the prefix, so
  the passage alone answers it (LAMBADA's construction), and
- **novel** — it did not, so only language knowledge can.

Two scores per checkpoint. **EM**: greedy-decode from the prefix, take the
first word, strip punctuation, exact match against the gold word — a synonym
or an inflection scores zero. **MC**: four-way multiple choice against three
distractors drawn from the same file with similar frequency and length and
absent from the prefix, ranked by total log-probability of each choice's
tokens (the LAMBADA / HellaSwag protocol); chance is 25%. The whole file is
1.07 MB, committed under `golden/`, deterministic from `--seed 7`.

| | `ckpt_hindi_mixed18k` | `ckpt_hindi_full` | `ckpt_hindi_v4` | `ckpt_hindi_350m` (bytes) |
| --- | --- | --- | --- | --- |
| corpus / steps | Wikipedia + Wikisource, 18k | Wikipedia (full), 6k | Wikipedia (30%), 6k | Wikipedia 107 MB, 6k |
| **all 600, EM / MC** | **11.2% / 85.8%** | 6.3% / 76.7% | 6.7% / 76.5% | 1.5% / 51.8% |
| Wikipedia | 12.3 / 87.0 | 9.7 / 84.0 | 9.7 / 85.3 | 2.7 / 60.7 |
| Wikisource | 10.0 / 84.7 | 3.0 / 69.3 | 3.7 / 67.7 | 0.3 / 43.0 |
| in_context | 15.7 / 88.3 | 8.0 / 78.3 | 8.3 / 77.7 | 1.7 / 52.3 |
| novel | 6.7 / 83.3 | 4.7 / 75.0 | 5.0 / 75.3 | 1.3 / 51.3 |
| Wikipedia / in_context | 17.3 / 90.7 | 12.7 / 86.0 | 12.0 / 86.0 | 3.3 / 60.0 |
| Wikipedia / novel | 7.3 / 83.3 | 6.7 / 82.0 | 7.3 / 84.7 | 2.0 / 61.3 |
| Wikisource / in_context | 14.0 / 86.0 | 3.3 / 70.7 | 4.7 / 69.3 | 0.0 / 44.7 |
| Wikisource / novel | 6.0 / 83.3 | 2.7 / 68.0 | 2.7 / 66.0 | 0.7 / 41.3 |

The byte model sees a quarter of the context (512 bytes ≈ 200 characters
against 512 tokens ≈ 2,000), and its generation budget is 48 bytes so a
whole word fits; its first pass at 12 bytes scored 0.0 EM everywhere, a
truncation artefact rather than a result, which is why the scorer scales
the budget for byte checkpoints.

Six readings.

- **MC is the number to quote.** 86% against a 25% floor: the best model
  reliably knows which of four plausible Hindi words fits a sentence. EM is
  low by construction — reproducing the one word the author wrote, with no
  credit for synonyms, is hard for a fluent human on the novel items — and is
  useful for ranking models, not as an absolute.
- **The register result transfers to accuracy.** On literature the mixed
  model is 15 MC points ahead of the Wikipedia-only model and 3× its EM;
  on Wikipedia the two are 3 points apart. Same shape as §17's bits/byte.
- **More Wikipedia did not help accuracy.** The 30%-dump and full-dump
  models are indistinguishable (76.5 vs 76.7 MC, 6.7 vs 6.3 EM) — §11's
  0.007 bits/byte at fixed compute, seen from the other side. The whole
  accuracy gain in the table is the second register and the longer schedule.
- **The tokenizer is worth 34 MC points.** The byte model at the same trunk
  and budget scores 51.8% — above chance, so it knows some Hindi, but
  §7's 0.162 bits/byte is here the difference between a coin-flip-and-a-half
  and reliable: less context per window, and a word is a 15-byte sequence it
  has to get right byte by byte.
- **Copying is worth less than knowing.** in_context items are easier for
  both models, but the MC gap between the two types is 5–8 points; most of
  the 86% is language knowledge, not induction-head copying. On EM the gap
  is 2× — when the exact word is on the page the model can fetch it.
- **This is still not factual accuracy.** A cloze on held-out text scores
  whether the model knows Hindi, not whether it knows the world. Question
  answering with verified answers is the next set to build, and it is a
  data-writing job; the scorer already takes any JSONL with `prefix`,
  `answer`, `choices` and `answer_idx`.

Chance for MC was checked the honest way: an untrained tiny model scores it
in the test suite (`golden_items_are_well_formed_and_the_scorer_runs`),
which also pins the set's contract — the gold word is in the prefix exactly
when the item says so, no distractor is, and the blank is the very next word.

## 20. Fine-tuning to answer questions

The base model continues text; asked a question it produces the article or
story that would follow those words. This section teaches it the other
thing, with the only instruction data a stdlib-only project can make for
itself: **the corpus's own subjects and lead sentences.** `make_qa.py`
turns every Wikipedia article into one pair — a question about its title in
one of six phrasings, and the article's first one or two sentences as the
answer —

    प्रश्न: काशी क्या है?
    उत्तर: काशी नगरी वर्तमान वाराणसी शहर में स्थित पौराणिक नगरी है।

56,478 pairs from 71,073 articles (the rest have no lead that reads as a
definition), mean answer 173 characters, split **by article** 98 / 2 so the
1,129 held-out questions are about subjects whose article the model saw in
pretraining but whose question it never did. That is what "answering" can
mean at 364M: recall of what it read, in a format it was shown.

`finetune.py` packs the pairs into 6,806 rows of 512 tokens (an example
never straddles two rows), masks the prompt to `-1` so the **loss lands on
answer tokens only** (73% of positions), and otherwise runs `train.py`'s
machinery from `ckpt_hindi_mixed18k`: AdamW at lr 5e-5, cosine to 5e-6,
2 epochs = 1,702 steps at batch 8, bf16, grouped dispatch, gradient
checkpointing, bias updates after every step. 15 minutes.

| held-out answer loss | |
| --- | --- |
| before | 3.719 |
| step 249 | 3.325 |
| step 999 | 3.222 |
| step 1701 (end) | **3.202** |

Most of the drop is in the first 250 steps — the format — and the curve
flattens toward the model's ordinary loss on Wikipedia lead sentences.

`eval_qa.py` scores the same held-out questions three ways, with the base
model prompted through the same template so the comparison is on one axis.
**MC**: the gold answer against three other held-out answers, ranked by
mean log-probability per token (chance 25%) — does it know *which* answer
belongs to the question. **F1**: SQuAD's token F1 between the greedy answer
and the gold one. **subj**: does the decoded answer even name the subject
asked about.

| | `ckpt_hindi_mixed18k` (base) | **`ckpt_hindi_qa`** |
| --- | --- | --- |
| MC (400 questions) | 43.0% | **50.2%** |
| token F1 (100 decoded) | 6.3 | **21.8** |
| names the subject | 12% | **81%** |
| answer shape | runs on for 96 tokens, loops, or answers a different question | one to two sentences, encyclopaedic, stops at EOS |

Three readings.

- **It learned to answer.** Subject-mention went from 12% to 81% and F1
  tripled: the model now produces a definition of the thing asked about, in
  the register of a lead sentence, and stops. The base model, given the
  same prompt, mostly wandered into narrative or repeated a phrase 96 tokens
  long.
- **It did not learn much more than it already knew.** MC moved 43 → 50
  against a 25% floor. The base model could already half-recognise which
  answer belonged to which subject; the fine-tune added seven points,
  which is format (it now expects an answer to follow) more than recall.
  Decoded answers name the subject and then attach it to a *plausible
  category* — an obscure cricketer becomes a television serial, a saint a
  BJP politician, a state song a Sony show — because at 0.5 epochs a 364M
  model has the shape of Wikipedia but few of its facts. Every date and
  place in the answers should be read as fiction.
- **Greedy decoding loops.** Two of six printed samples degenerate into a
  repeated phrase. `generate()` now takes `repetition_penalty` (CTRL's
  rule, off by default; the tests confirm 1.0 is bit-identical to before),
  and `serve.py`'s question mode uses 1.3, which breaks the loops without
  changing the answers that were already fine.

What would move MC: more pretraining (the corpus was seen half a time), and
question types that are not definitions. The pipeline is in place for both —
`make_qa.py` is one template away from "where is X" or "when was X born",
and `eval_qa.py` scores any file with `question` / `answer` / `title`.

`serve.py --ckpt ckpt_hindi_qa.pt` serves the result: the page detects the
checkpoint's `qa_template` and offers *answer a question* beside *continue
the text*, the base behaviour, on the same weights.

## 21. Twice the steps: 18k → 36k, and what reaches the answers

§18 ended with "the curve had not flattened" and §20 with "what would move
MC is more pretraining". So: the same run, continued. `ckpt_hindi_mixed18k`
was copied to a new name and `train.py --resume --steps 36000` picked it up
at step 18,000 — weights, AdamW moments and sampler position — with the
cosine now spanning 36k steps. Extending a *finished* run lands mid-cosine,
at 3e-4 against the 3e-5 the weights had annealed to, so `--rewarmup 500`
(new) ramps the lr from zero back to the schedule over 500 steps instead of
jumping. 18,000 more steps, 73.7M tokens, 1 h 58 min; the model ends at
epoch 1.17, so its second half was still 80% first-pass text.

**The restart costs a bump and pays it back.** Held-out loss on the mixed
split, same windows as every earlier eval:

| step | 18k (start) | 19k | 21k | 23k | 25k | 26k | 29k | 32k | **36k** |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| val | 4.302 | 4.507 | 4.456 | 4.385 | 4.316 | 4.287 | 4.197 | 4.141 | **4.099** |

The first eval is 0.2 *worse* than the checkpoint it resumed from: the lr
ramp undid some of the anneal, as a warm restart does. The right comparison
is against the original run at matched lr — 4.70 at step 9k, lr 2.5e-4 —
and by that measure the resumed run was ahead throughout. It crossed below
the old best at step 26k and set a new one at every eval after.

| | `ckpt_hindi_mixed18k` | **`ckpt_hindi_mixed36k`** | Δ |

| Wikisource bits/byte | 0.6794 | **0.6479** | −0.032 |

**−0.03 bits/byte on both registers** — more than the recipe change (§9),
fine-grained experts (§10) and the data lever (§11) together, and the
second-largest single move in the log after the tokenizer. The golden set
moved a point: its MC column is near saturation at 86%, where the items
left are ones with several genuinely plausible choices, and its stricter
EM column moved 3 points on Wikipedia and none on literature. Compression
keeps improving after the cloze test stops being able to see it.

### The same fine-tune, from the better base

§20's recipe unchanged — the same 55,349 pairs, 2 epochs, lr 5e-5 — from
`ckpt_hindi_mixed36k`, giving `ckpt_hindi_qa36k`. 21 minutes.

| | base 18k | tuned 18k | base 36k | **tuned 36k** |
| --- | --- | --- | --- | --- |
| held-out answer loss | 3.719 | 3.202 | 3.488 | **2.984** |
| MC, answer recognition (chance 25%) | 43.0 | 50.2 | 43.5 | **51.2** |
| token F1 | 6.3 | 21.8 | 8.4 | **23.0** |
| names the subject | 12 | 81 | 36 | **86** |

Three readings.

- **Pretraining carries straight through.** The tuned 36k model's answer
  loss is 0.22 below the tuned 18k model's — the entire gap between the two
  bases, preserved by the fine-tune. And the untuned 36k base already names
  the subject three times as often as the 18k base did (36% vs 12%) when
  handed the question template: the extra pretraining alone made it more
  willing to talk about the thing it was asked about.
- **Recognition barely moves.** MC went 50.2 → 51.2. Twice the pretraining
  compute, −0.03 bits/byte, and the model is one point better at telling
  which of four lead sentences belongs to a subject. F1 +1.2, subject
  mention +5. What improves with compute is *how* it answers; *what* it
  knows about any particular subject is set by how many times that subject
  appeared in 140M tokens, which is usually once. The decoded answers are
  the same kind of wrong as §20's: fluent, the right shape, a plausible
  category, invented dates — and one repeated-name loop in six samples even
  now.
- **This is the ceiling of the corpus, not the model.** A subject that
  appears in one article, read 1.2 times, is not a memory; it is a
  perplexity. Moving MC materially means more mentions per fact — a larger
  corpus with redundancy, or many epochs — or retrieval, where the lead
  sentence is looked up rather than recalled. Both are further than this log
  goes.

## 22. Three scripts, one budget: Hindi + English + Python with a 32k tokenizer

Everything to §21 is Hindi. Sarvam's models are not: the tokenizer covers
22 languages, and the point of the low Indic fertility is that Hindi shares
a vocabulary with English and code without paying for it. So: the same
preset, recipe and budget as `ckpt_hindi_mixed36k` — combo configuration,
36k steps at 8 × 512, lr 6e-4, seq-balance and z-loss on — on a corpus that
adds English and Python to the §17 Hindi, read through a 32k tokenizer
trained on all three. `experiments/build_multi.sh`, `experiments/run_multi.sh`.

### The corpus and the tokenizer

| part | source | text | documents |
| --- | --- | --- | --- |
| Hindi | `data/mixed.txt` (§17: Wikipedia + Wikisource) | 1,323 MB | 224k |
| English | English Wikipedia through `fetch_hindi.py` with the Devanagari filter off (167 MB, the dump server dropped the connection) + C4 through `fetch_web.py` (367 MB) | 523 MB | 114k |
| Python | codeparrot-clean through `fetch_code.py`, hand-written-looking files only | 257 MB | 33k |
| | interleaved, shuffled | **2,104 MB** | 372k |

The last 2% of the English and Python documents are held out as
`bench_english.txt` and `bench_python.txt` before anything is trained,
the same way `make_bench.py` holds out Hindi. `multi32k` was trained on a

| tokenizer | `bench_hindi` | `bench_wikisource` | `bench_english` | `bench_python` |
| --- | --- | --- | --- | --- |

| `multi32k` (32k, three scripts) | 9.55 | 9.05 | **4.33** | **4.42** |

Doubling the vocabulary and spending the new half on Latin script costs
Hindi 1–4% of its compression and doubles or triples English and Python's:
the 16k Hindi tokenizer was splitting English into 2.9 tokens a word and
Python into 7.2, near byte level. The encoded corpus is 322.1M tokens at
6.53 bytes/token — roughly 140M Hindi, 120M English, 60M Python — of
which the 36k-step budget (147.5M tokens) reads 0.51 epochs.

### The run

The 32k head adds 33.5M parameters of embedding and unembedding: 397.7M
total, 173.5M active (43.6%). 36k steps took 4 h 2 min at ~10.2k tok/s,
imbalance settling at 1.5–1.7×, own-val loss 6.88 at step 1k → 4.441 at
36k (0.981 bits/byte on the mixed val split, a number comparable to nothing
else in this log because the split is three languages). What is comparable
is the four benchmarks, each model through its own tokenizer:

| bits/byte | `ckpt_hindi_mixed36k` (364M, 16k) | **`ckpt_multi36k`** (398M, 32k) | Δ |
| --- | --- | --- | --- |
| Hindi Wikipedia | **0.5876** | 0.6455 | +0.058 |
| Hindi Wikisource | **0.6479** | 0.7165 | +0.069 |
| English | 2.3010 | **1.5360** | −0.765 |
| Python | 3.7700 | **1.0774** | −2.693 |

Three readings.

- **The Hindi cost is the token budget, not the vocabulary.** The
  tokenizer's 1–4% is a small part of +0.06; the rest is that the same
  147.5M training tokens now hold ~64M Hindi tokens instead of 147.5M. The
  §18 → §21 step measured what halving the Hindi budget is worth at this
  point on the curve: 18k steps cost 0.03 against 36k. Twice that, for a
  model that also reads two other scripts, is the trade.
- **English and Python are learned, not merely tokenized.** The Hindi-only
  model's 2.30 / 3.77 is what a Devanagari model does with Latin text it
  has seen only as loanwords — worse than a byte model would. 1.54 bits/byte
  on held-out English at 120M tokens of English is a real, small language
  model; 1.08 on Python reflects how repetitive code is. The samples say
  the same: `def fibonacci(n):` completes as a syntactically valid
  two-line function with an invented call, then a second `def` whose
  argument list repeats one name to the end of the budget; `Mumbai`
  continues as boilerplate business prose, `मुंबई` as a Wikipedia biography.
- **The model is the same model.** Same 140M active parameters in the
  experts and attention; only the head grew. What changed is what the
  budget bought. The log's answer to "what would a bigger corpus do" (§21)
  has a second half now: a *broader* corpus at the same budget spreads the
  same competence thinner, and only more steps get it back.

## 23. Questions in three languages

§20's recipe, extended to the languages the model now has. Two new pair
builders: `make_qa_en.py` does for English Wikipedia what `make_qa.py`
does for Hindi (`Question: What is Digimon?` / the lead sentence), and
`make_qa_py.py` turns every documented top-level function in the Python
corpus into two kinds of pair — *write* (`Write a Python function
\`add\`: return the sum of two numbers.` → the source, docstring included)
and *explain* (the source with its docstring removed → the docstring's
first sentence) — parsed with `ast`, held out by file. `experiments/run_qa_multi.sh`.

| pairs | train | held out |
| --- | --- | --- |
| Hindi (`make_qa.py`, capped from 55k so it does not drown the rest) | 20,000 | 1,129 |
| English | 6,744 | 137 |
| Python (write + explain, `--max 20000` before the length filter) | 10,763 | 269 |
| | **37,507** | 1,535 |

Packed: 5,642 rows of 512, 1.75M answer tokens (61% of positions). Two
epochs, 1,410 steps, lr 5e-5, 9½ minutes; held-out answer loss 3.893 →
3.315. `ckpt_multi_qa.pt` carries three templates (`hi`, `en`, `py`) and
`serve.py` picks by script. Scored per language on 300 held-out questions
for MC (all 137 for English) and 60 decoded:

| | MC % (chance 25) | token F1 | names the subject % |
| --- | --- | --- | --- |
| Hindi, base `ckpt_multi36k` | 40.0 | 5.1 | 15.0 |
| Hindi, tuned | **48.3** | **18.7** | **65.0** |
| English, base | 34.3 | 8.7 | 38.3 |
| English, tuned | **37.2** | **20.6** | **70.0** |
| Python, base | 45.0 | 4.8 | 18.3 |

- **The format transfers; the facts are where the tokens were.** The
  tuned model learns to answer in all three languages from one fine-tune,
  and the Hindi columns land 3 MC points and 20 subject-mention points
  under the Hindi-only model's — the same gap §22 measured in bits/byte,
  now in answers: half the Hindi tokens is half the Hindi facts.
- **Python is the easy language.** MC 72% is the highest recognition
  number in the log, and it is the least surprising: telling which of four
  function bodies matches a description is mostly matching identifiers,
  and a function's docstring is right there in the *write* pairs. The
  decoded answers are the interesting failure — the base model already
  writes the function's docstring and first comment correctly and then
  invents the body; the tuned one writes a shorter, more plausible body
  that is usually still wrong. What separates this from a coder is
  the coder plan's 2.8B tokens (`docs/CODER_PLAN.md`), not the recipe.
### What it answers, decoded (`ask.py`, temperature 0.3, repetition penalty 1.3)

```
Q: काशी क्या है?
A: काशी भारत के उत्तर प्रदेश राज्य का एक प्रमुख नगर है। यह इसी नाम की तहसील का
   मुख्यालय भी है।                                                    <- correct

Q: गंगा नदी के बारे में बताइए।
A: गंगा नदी भारत के उत्तर प्रदेश राज्य का एक प्रमुख शहर है।
   ("The Ganges river is a major city in Uttar Pradesh")               <- a river, called a city

Q: What is a volcano?
A: The island of the Sea of the Republic of the United Kingdom, also known as
   the Sea.

Q: Write a Python function `is_prime`: return True if n is prime.
A: def is_prime(n):
       \"\"\"Return True if n is prime.\"\"\"
       if not is_prime(_ns):
           return False
       return True
```

Every one stops cleanly at EOS, in the right language, in the right shape.
That is the whole of what the fine-tune taught, and the failure is uniform
across all three: **the template is learned and the slot is filled from the
prior, not from knowledge.** "X is a major city in Uttar Pradesh" is the
most probable Hindi Wikipedia lead sentence, so the Ganges gets it. The

completely and few new facts" — reproduced in three languages at once, and
it is why MC (recognition) moves much further than F1 (production).

- **English is the hard one**, at 37% MC and 6.7k pairs. The English
  Wikipedia slice is 167 MB against Hindi's 1.3 GB, and the pairs are
  1/3 as many; the model's English is mostly C4, which has no subjects
  to ask about.

## 24. English ↔ Hindi translation

The demo the three-language model exists for, decided in
`docs/TRANSLATE_PLAN.md` to run before the coder because it is a day of
GPU rather than a week. The base already writes both languages; what it
lacks is the alignment between them, which is what parallel text teaches.

**Data.** Samanantar (the AI4Bharat en-hi corpus, 8 parquet shards) and
the IIT Bombay English-Hindi corpus, through `convert_translate.py`:
3–200 words a side, length ratio under 3:1, the Hindi side mostly
Devanagari, de-duplicated on the English side, capped at 2M pairs. Every
pair becomes two items, `English: …\nHindi: …<EOS>` and `Hindi: …\nEnglish:
…<EOS>` (`lang` `en-hi` / `hi-en`), so the one checkpoint translates both
ways and the web page picks the direction from the script. 4M items pack
into 493,370 rows of 512 (105.7M answer tokens, 42% of positions) in 127 s
across 16 encoder processes; 2,000 pairs are held out for the loss curve,
and FLORES-200 devtest — 1,012 sentences, both directions — is the test
set, touched by no training data.

**Run.** `finetune.py` from `ckpt_multi36k`, one epoch = 61,672 steps at
batch 8, lr 1e-4 → 1e-5, warmup 500, eval every 2,000. This is the first
run long enough to need `--stop-at`, and it took three calls: the first
ran to 25,000 (2 h 44 min), the second was left to run to the end and
died after its step-48,000 save (the checkpoint said 47,999; the log
showed nothing past the phase header, because a `grep` in the pipe
buffers 4 KB at a time and the process took the buffer with it), and the
third resumed from `.last` and ran the remaining 13,672 steps in 1 h 28
min. 6 h 1 min of GPU in all, 2.55 steps/s throughout.

| step | 0 | 2k | 4k | 8k | 12k | 16k | 20k | 24k | 25k | 48k | 50k | 54k | 58k | 60k | **61,672** |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| held-out answer loss | 4.051 | 3.352 | 3.153 | 2.974 | 2.861 | 2.760 | 2.678 | 2.610 | 2.606 | 2.348 | 2.341 | 2.321 | 2.307 | 2.301 | **2.297** |

Steady and never flat: −0.26 between 25k and 48k, −0.05 over the last

**The number.** chrF on FLORES-200 devtest, greedy, `eval_translate.py`:

The full-devtest number (55 min at 1.6 s/sentence) is the one to quote:
**41.5 / 43.4**. The 50-sentence preview overstated en → hi by three
points — FLORES's first fifty are short news sentences, and the set gets
harder — and hi → en held. Against the plan's "in the 40s after one
pass": yes, at the bottom of them for en → hi, with the base at zero and
NLLB-600M, a model with 1.5× the parameters trained on 40× the pairs, at
about 55.

The base cannot do the task at all — handed `English: … Hindi:` it writes
English, and loops ("the year was a year of the year …"). 22,000 steps of
fine-tuning later the same weights produce Hindi sentences that carry the
structure and most of the content of the source: *Like some other experts,
he is skeptical about whether diabetes can be cured* → कुछ अन्य विशेषज्ञों
की तरह वह इस बात से भी अवगत हैं कि मधुमेह की … — right frame, "aware"
where "skeptical" should be, and *mice* rendered as माइनस, which is where
a 2M-pair, 400M-parameter translator slips: rare nouns, names, numbers.
Decoded from the finished checkpoint (`ask.py --mode translate`, greedy):

```
The train to Mumbai leaves at six in the morning.
  -> मुंबई के लिए ट्रेन सुबह छह बजे से रात को बंद है।
     ("The train for Mumbai is closed from six in the morning until night")

Where is the nearest hospital?
  -> नजदीकी अस्पताल कहां है?                                          <- correct

मुझे कल दिल्ली जाना है।
  -> I have to go to Delhi tomorrow.                                   <- correct
```

Two of three are clean. The third carries subject, destination and time
across and then invents the verb — *leaves* becomes *is closed until
night* — which is what a chrF in the low 40s looks like sentence by
sentence: most of the content, an unreliable predicate. Where it slips is
what the plan predicted: rare nouns, names, numbers. Where it holds is
everyday sentence structure in both directions, which is what the web
page's *translate* mode is for.

  250k   \"\"\"Find the index of a fibonacci number from the number of n\"\"\"

At 100,000 steps the completions were Python-shaped noise. At 250,000 they

boundary for the series, but read the samples and the loss until the first
non-zero appears.

### Instruction tuning at step 250,000: the first non-zero

Run at 36% of the schedule to decide whether the remaining 50 h of GPU
were worth spending. **They are: the pipeline produces a working coder.**

`ckpt_coder.pt` (step 250,000) tuned for one epoch on 293,691 pairs —
200,000 code_exercises, 43,728 OpenCodeInstruct, 40,000 glaive, 10,763
docstring pairs — 14,727 steps, 1 h, lr 5e-5, loss on answer tokens only.

| | base, step 250k | **instruction-tuned** |
| --- | --- | --- |
| held-out answer loss | 2.2808 | **1.1476** |
| HumanEval pass@1 | 0.0% (0/164) | 0.0% (0/164) |
| MBPP pass@1 (sanitized test) | 0.0% (0/257) | **5.1% (13/257)** |

**Thirteen MBPP problems execute correctly against their hidden tests.**
That is the first non-zero in this log, and it arrives at 36% of the
pretraining schedule, on 1.02B of 2.87B tokens. CodeParrot-110M reaches
~4% on HumanEval after 25B tokens; this is 5.1% on MBPP after 1.02B.

Three readings.

- **Instruction tuning is what converts the model's idiom into programs.**
  The base checkpoint scores zero on the same problems with the same
  decoder. Everything §25 observed — docstrings, `for`/`range`, correct
  `isinstance` — was latent capability that the base model could not aim
  at a task. 293k pairs aimed it.
- **The two benchmarks disagree, and MBPP is the right one to watch here.**
  MBPP's problems are short, self-contained and close in shape to the
  exercise pairs; HumanEval's are longer and need more compositional
  reasoning. A model that solves 5% of MBPP and 0% of HumanEval is exactly
  what a 400M model at a third of Chinchilla-optimal should look like.
  Expect HumanEval to stay at or near zero until much later, if it moves
  at all.
- **The answer loss was still falling when the epoch ended** (1.1476 at
  the last of 30 evals, a new best every time). The 200k cap on exercise
  pairs is leaving value unspent: the final tune at step 700,000 should
  run on more of the 1.29M, and `EX_CAP=0` is the knob.

#### What it means for the remaining budget

Proceed. The 450,000 steps left are now buying a known-good pipeline more
compute rather than testing whether there is one. Revised expectation for
the tuned step-700,000 checkpoint: **MBPP in the low teens, HumanEval in
low single digits**, on the reasoning that MBPP went 0 → 5.1% for the
first 36% of pretraining plus a capped tune, and the remaining 64% plus an
uncapped tune is a larger increment than that but not a multiple of it.
That is below the plan's original 10-25% on HumanEval, and the honest
number to quote is MBPP's.

#### The 0.0% was a prompting artifact, and finding it changed the number

`eval_code.py` chose `question` mode for any checkpoint carrying
`qa_templates` and `continue` for any that did not, with no override. That
is right for MBPP, whose items are prose task descriptions, and wrong for
HumanEval, whose native form *is* a continuation: a signature and docstring
to complete. Asked as a question, the tuned model writes a fresh function
instead of continuing the given one, and scores 0.0%. Asked to continue,
the same weights score 3.0%.

`--mode {continue,question}` now forces it. Two things follow.

- **Report which mode produced a number.** A 0.0% that is really 3.0% is
  the kind of error that survives into a paper.
- **Instruction tuning genuinely cost a little raw continuation ability**:
  4.9% base against 3.0% tuned, both in `continue` mode, a fair comparison.
  The tune bought 0 -> 12.5% on MBPP and paid ~2 points of HumanEval for
  it. That is a real specialisation trade, not an artifact, and at this
  scale it is clearly worth it.

### A review of the training loop, and what it changes about the readings above

Prompted by a corrupted resume point (below), `train.py` was read end to
end on 2026-09-12 rather than patched further. Two findings, one of which
revises earlier conclusions in this section.

**1. The val-loss estimate is much noisier than the deltas being read off
it.** `evaluate()` averages `iters=20` batches of `batch_size` windows.
On the coder run that is 160 windows of 512 tokens: 82k tokens out of a
**278M-token val split, 0.03% of it**. Measured directly on
`ckpt_coder.pt` at step 265,000, six different window sets of that size
give:

| window set | 0 | 1 | 2 | 3 | 4 | 5 |
| --- | --- | --- | --- | --- | --- | --- |
| val loss | 3.2617 | 3.1139 | 3.2109 | 3.2203 | 3.4761 | 3.3695 |

Spread 0.36, standard deviation 0.125. With more windows: 3.3050 +/-
0.039 at iters=100, 3.3133 +/- 0.019 at iters=400.

The fixed seed does real work here -- successive evals see the *same*
windows, so the comparison between two steps is paired and the curve's
large moves are trustworthy. Phase 2's fall of 0.160 is far outside the
noise and stands. **But the small features are not interpretable.** The
"plateau" at the end of phase 1 (3.436 -> 3.451, four evals) and the
second at 195k-225k were each about 0.015 on a statistic whose window-set
standard error is 0.125; they say something about 160 particular windows
and nothing dependable about the model. The §1 analysis of whether the
learning rate was too high was, in hindsight, reading tea leaves, and the
step-150,000 "decision point" was answered by a 0.068 move that is only
half a standard error. Nothing was decided wrongly -- the conclusion "do
not change the learning rate" was right for other reasons, and the run
has improved steadily since -- but the evidence was weaker than it was
presented as.

`--eval-iters` now exposes this; 200 costs ~30 s per eval, under 2% of a
33-minute interval, and cuts the error ~3x. It is deliberately **not**
changed mid-run: adding windows shifts the mean and would break the
current curve's comparability with its own earlier points. A related
consequence worth stating: `<out>` is selected by this statistic, so the
"best" checkpoint is picking between numbers separated by less than their
own sampling error, and is better thought of as "a good checkpoint near
the end" than as the genuine optimum.

None of this touches §1-24. Those numbers come from `eval_bench.py`,
`eval_golden.py`, `eval_qa.py`, `eval_translate.py` and `eval_code.py`,
which score *entire* held-out files or benchmark sets with no sampling.

**2. Checkpoint writes were not atomic, and a kill destroyed the resume
point.** `torch.save` writes in place. The coder run was killed while
writing the 4.8 GB `ckpt_coder.pt.last` at step 265,000, leaving a
truncated zip that `torch.load` rejects with "failed finding central
directory". Worse than the loss itself: the scheduled task then restarted
training every 30 minutes, hit the unreadable file, died in 11 seconds,
and repeated -- self-healing machinery faithfully repeating a fatal error
looks exactly like self-healing machinery working, and it went unnoticed
for about three hours.

Both fixed. `atomic_save()` writes beside the target and `os.replace`s it,
which is atomic within a volume, so a kill can no longer destroy the
previous checkpoint; `train.py` and `finetune.py` both use it for every
checkpoint write. And `--resume` now falls back: if the resume point is
unreadable it loads `<out>` instead, warns that it is continuing without
optimizer moments or sampler position, and carries on. Starting from step
zero, or looping on a fatal error, are both worse than a dent in the
curve.

### Running it without a terminal

Three operational findings, all paid for in wall clock, and the third is
the one worth carrying to any long run on Windows.

The `bash.exe` on PATH is the WSL stub, not Git Bash.

A long run needs an owner that outlives the terminal. Training is now a
Windows scheduled task firing every 30 minutes, whose wrapper exits
immediately if a `train.py` process is already alive: a firing during
healthy training is a no-op, a firing after a crash restarts from
`ckpt_coder.pt.last`, and the worst case after any interruption is 30
minutes idle plus at most 33 minutes of unsaved steps.

**A task registered with `/it` still dies to Ctrl+C in the interactive
console.** An interactive token means it shares that console, so a shell
exiting or a tool call being interrupted delivers Ctrl+C to the trainer as
well. It reads as `Last Result: -1073741510` on the task
(`STATUS_CONTROL_C_EXIT`) and a bare `^C` at the end of the stderr log,
and it killed the run twice — phase 1 at step 10,000, phase 2 at step
105,000, 2 h 51 min of idle GPU between them. The wrapper now launches the
trainer through `start`, which gives it a console of its own; nothing in
the interactive console can signal it. `TASKS.md` holds the commands.
