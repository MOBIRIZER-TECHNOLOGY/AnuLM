Foundations

1

The smallest language model

By the end of this chapter you will have trained a language model on your own laptop, from nothing, in about two minutes, and you will know exactly what the number it prints means. Every model in this book, up to the one that listens and sees in Chapter 13, does the same single job you meet here.

1.1 One job: guess what comes next

A language model reads some text and guesses what comes next. That is the whole job. Everything else, from answering questions to writing code, is built on top of doing that one guess well.

Computers store text as bytes, numbers from 0 to 255. English letters are one byte each; a Hindi letter like भ takes three. In this chapter the model reads and writes bytes directly, which means it works on any language without any setup. (Chapter 3 replaces bytes with tokens, which is faster.)

So the model's job, precisely: given the bytes so far, give a probability to each of the 256 possible next bytes.

After "To be or not to b", the model you are about to train gives e a 56% chance. It has never been told about Hamlet. It worked out from examples that after b in this kind of text, e is common.

How we score a guess. If the real next byte was e and the model gave it probability 0.56, its surprise is −log(0.56) = 0.58. A model that was certain and right scores 0; one that gave the right answer 1% scores 4.6. The loss is the average surprise over many real next bytes, on text the model did not train on. Lower is better. It is measured in nats; divide by 0.693 to get bits.

One number anchors everything: a model that knows nothing gives every byte 1/256, and its loss is log(256) = 5.545. Any model worth having must beat that.

1.2 A model that only counts

The simplest model that beats a blind guess doesn't learn anything in the usual sense. It counts. For every byte in the training text, it notes which byte came next, and keeps a 256 × 256 table of counts. To guess, it looks up the row for the current byte.

This is called a bigram model ("two bytes"). Here is all of it:

# lab.py, bigram()
counts = torch.ones(256, 256)                   # every pair starts at 1
counts.index_put_((train[:-1], train[1:]),      # +1 for each (this, next)
                  torch.ones(len(train) - 1), accumulate=True)
probs = counts / counts.sum(1, keepdim=True)    # each row now sums to 1
loss = -probs[val[:-1], val[1:]].log().mean()   # average surprise on unseen text

On Shakespeare it scores 2.49: already far better than 5.545. And yet, ask it to write and it produces this:

ROMEO:
wire!
JUELLIAndirstyo iod w,
I bel Hadvabr'lllly anre braunco seary hor, iveandeerph dileatore

Each pair of letters is plausible; the words are not. The model sees exactly one byte back, so it cannot know it is halfway through Romeo.

Note

Every count starts at 1, not 0, so that no pair is ever impossible (add-one smoothing). The price shows in its samples: once in a while it picks a byte that never appears in English and prints �.

1.3 Looking further back: a tiny transformer

To do better, the model has to look further back than one byte and decide for itself which earlier bytes matter. That is what a transformer does.

Read the figure from the bottom. Each byte becomes a list of 128 numbers (an embedding), plus a second list that says where it sits in the text. Then four identical layers each do two things:

  • Attention lets every position look back at all earlier positions and pull in what is relevant. In "To be or not to b", the last b can attend to the first be.
  • An MLP, a small two-layer network, then processes what was gathered.

Each layer adds its result to a running representation rather than replacing it, so information is never lost on the way up. At the top, an output head turns the final 128 numbers into 256 scores, one per possible next byte, and softmax turns the scores into probabilities.

The heart of it is five lines:

# lab.py, Block.forward()
q, k, v = self.qkv(self.ln1(x)).split(D, dim=2)          # what I want, what I have, what I give
q, k, v = (t.view(B, T, self.heads, D // self.heads).transpose(1, 2) for t in (q, k, v))
y = F.scaled_dot_product_attention(q, k, v, is_causal=True)   # never look ahead
x = x + self.proj(y.transpose(1, 2).reshape(B, T, D))         # add what attention found
return x + self.mlp(self.ln2(x))                              # add what the MLP made of it

is_causal=True is what makes this a language model: position t can see positions 0 to t and nothing after, so it can't cheat by reading the answer.

This model has 875,520 parameters: numbers it can adjust. At the start they are random, and it guesses no better than blind.

1.4 Learning by being surprised

Training repeats one small loop thousands of times: show the model a batch of real text, measure its surprise at every real next byte, and nudge every parameter slightly in the direction that would have made it less surprised.

# lab.py, main()
for step in range(1, steps + 1):
    x, y = batch(train, ctx, 32, g)       # 32 windows of 128 bytes; y is x shifted by one
    _, loss = model(x, y)                 # how surprised was it?
    opt.zero_grad(set_to_none=True)
    loss.backward()                       # which way should each parameter move?
    opt.step()                            # move it a little (AdamW)

The direction comes from loss.backward(), which computes the gradient: for each of the 875,520 parameters, how much the loss would change if it moved. The optimizer, AdamW, takes a small step downhill.

Within 200 steps it matches the table of counts. By 2,000 it reaches 1.75, and its writing has changed character:

AUTOLYCUS:
In is good I entring thalt some the fail of the demear
Hereful man, for her for since; and for the fair:
Who here and would gider the alooker:

Real names, line breaks where a play has them, speeches that start with a speaker. The words are still often wrong. It is a 0.9M-parameter model that has read about one megabyte, for two minutes.

Key takeaways

  • A language model has one job: a probability for every possible next piece of text.
  • Loss is average surprise on text it did not train on; a blind guess over bytes scores 5.545.
  • Counting pairs already halves the loss; looking further back is what a transformer adds.
  • Training is one loop: predict, measure surprise, nudge every parameter downhill, repeat.
  • The same loop, scaled up about 450×, is how the AnuLM base model was made.
2

Your own data

A model is mostly its data. This chapter turns text on your own disk into a corpus you can train on: documents, deduplication, filtering, a validation split that tells the truth, decontamination against the benchmarks you'll be scored on, and the question that comes before all of them: are you allowed to use this text at all? Every one of these steps fails silently. Nothing crashes; the model trains; and it learns from duplicates, from list debris, or from the very test it is later graded on.

2.1 The pipeline

You build each step as a small function in course/build/data.py, checked against the repository's own tools: bpe.py, filter_prose.py, fetch_hindi.py, convert_parquet.py and train.py.

2.2 Documents

The repository stores a corpus as one big text file, with documents separated by three newlines (DOC_SEP). The boundary matters later: Chapter 3 puts an end-of-document token there, so the model learns where one text stops and the next begins, instead of reading two articles as one.

DOC_SEP = "\n\n\n"
def split_documents(text):
    return [d for d in text.split(DOC_SEP) if d.strip()]

2.3 Cleaning: duplicates, debris and scripts

Duplicates. Web text repeats itself: mirrored pages, boilerplate, quoted articles. A model trained on a document ten times memorises it and learns everything else less. The simplest fix removes exact copies by hashing each document and keeping the first one seen, in order:

def exact_dedup(docs):
    seen, kept = set(), []
    for d in docs:
        h = hashlib.sha1(d.encode("utf-8")).digest()
        if h not in seen:
            seen.add(h)
            kept.append(d)
    return kept, len(docs) - len(kept)

Debris. Wikipedia dumps carry infoboxes, station lists and filmographies that survive cleaning as bare lines. filter_prose.py measured that on the Hindi dump: the median article has 64% of its lines ending in a sentence mark, the bottom quarter under 34%. A model trained on that learns to write lists. The filter drops short lines that don't end a sentence (. ! ? or the Devanagari danda ।), then drops a whole document if too few of its lines are sentences or too little text remains. The title, the first paragraph, is kept.

Scripts. A share-of-script function tells you what language a document mostly is, cheaply: the fraction of its characters in one Unicode block. Devanagari is U+0900 to U+097F.

2.4 A validation split that tells the truth

A validation set must look like the training data. The obvious way, the last 10% of the file, fails whenever the corpus was built one source at a time: then the tail is one source. The repository's interleaved_split instead holds out every tenth chunk across the whole file:

def interleaved_split(data, chunk, every=10):
    chunks = [data[i:i + chunk] for i in range(0, len(data), chunk)]
    val   = [c for i, c in enumerate(chunks) if i % every == every // 2]
    train = [c for i, c in enumerate(chunks) if i % every != every // 2]

In the lab's corpus, Hindi articles then Shakespeare, the whole corpus is 69% Devanagari. The tail is 0%: a validation loss read on it would measure English only. The interleaved split is 69%, the corpus's own mix.

2.5 Decontamination

A benchmark measures something only if the model hasn't seen it. Benchmark items leak into training data constantly, through copies, quotes and model-generated text. The standard test, used by the Llama and phi papers and by tools_contamination.py, flags a benchmark item if it shares any run of 13 consecutive words with the training text.

WORDS = re.compile(r"[a-z0-9_ऀ-ॿ]+")
def word_ngrams(text, n=13):
    w = WORDS.findall(text.lower())
    return {tuple(w[i:i + n]) for i in range(max(len(w) - n + 1, 0))}

Look at the pattern. The repository's version is [a-z0-9_]+: Latin letters, digits and underscores. It was written for Python benchmarks (MBPP, HumanEval), where that is exactly right. But run it on Hindi and it finds no words at all, so it reports any Hindi text as clean, however much of a benchmark it copies. Your version adds the Devanagari block, and gives the same answer on English.

The lab hides 5 Hindi and 5 English benchmark passages inside training documents. Your matcher finds all 10, with no false alarms. The repository's finds all 5 English ones and 1 of the Hindi ones, and that one only because the passage happened to open with map coordinates (26°37′24′′N 79°08′40′′E…): it matched the digits, not the Hindi. The repository's Hindi benchmark is protected a different way: make_bench.py compares Devanagari-only signatures. The lesson stands: a check that sees nothing reports "clean". Test your checks on the scripts you actually use.

3

Build the tokenizer

Chapter 1's model read one byte at a time. That works for any language, and it's expensive: a Hindi letter is three bytes, so a 1,024-position window holds only about 400 Hindi characters, a few sentences. A tokenizer groups bytes that often occur together into single tokens, so the same window holds far more text, and the model learns more per step. In this chapter you build AnuLM's tokenizer, byte-level BPE, from scratch, prove it matches the repository's bpe.py merge for merge, and measure what it buys.

3.1 The idea: merge the most common pair

Byte-pair encoding (BPE) starts with the 256 possible bytes as its vocabulary. It finds the most frequent pair of adjacent tokens in your text, makes that pair a new token, and repeats. After a few thousand merges, common words and word pieces are single tokens:

Because every text is made of bytes, nothing is ever "unknown". A script the tokenizer never saw, such as Tamil in a Hindi-and-English tokenizer, simply falls back to smaller pieces, down to single bytes.

3.2 Training

The text is first cut into chunks: a word together with the spaces before it, or a run of spaces. Merges never cross a chunk boundary, so a token never glues the end of one word to the start of the next. Then the loop:

# build/solutions/ch03.py, train_bpe
chunks = Counter(c.encode("utf-8") for c in CHUNK_RE.findall(text))     # CHUNK_RE = r"\s*\S+|\s+"
words = [(list(c), f) for c, f in chunks.items() if 2 <= len(c) <= MAX_TRAIN_CHUNK_BYTES]
while 256 + len(merges) < vocab_size - 1:              # one id stays free for end-of-document
    counts = Counter()
    for seq, f in words:
        for p in zip(seq, seq[1:]):
            counts[p] += f                               # each unique chunk, weighted by its count
    best = max(counts.values())
    if best < 2:
        break                                            # nothing left worth an id
    pair = min(p for p, c in counts.items() if c == best)   # ties: the smallest pair
    merges.append(pair)
    words = [(_merge(seq, pair, 256 + len(merges) - 1), f) for seq, f in words]

Two details decide whether your merges match bpe.py's exactly. Ties: when several pairs are equally frequent, bpe.py's heap picks the smallest pair, so yours must too. And stopping: a pair seen only once isn't worth an id.

This plain loop recounts every pair after every merge. bpe.py keeps the counts up to date incrementally and finds the best pair with a heap: same merges, same order. In the lab, for 767 merges, your loop takes 10.6 seconds and bpe.py 0.4. On the 12.6 MB Hindi corpus, bpe.py trains 16,384 ids in 10 seconds.

3.3 Encoding and decoding

To encode a chunk, start from its bytes and repeatedly apply the merge that was learned earliest among the pairs present, until none applies. Applying merges in training order is what makes the result unique; merging greedily from left to right gives different tokens, which no model trained with this tokenizer has ever seen.

Decoding is simpler: join each token's bytes and decode UTF-8. That makes decode(encode(x)) == x exact for any text, including spaces, tabs and emoji.

3.4 Documents end with a token

Chapter 2 kept document boundaries for this. encode_documents puts one extra id, end-of-document (EOS), after every document. It is the id kept free during training, 256 + len(merges). EOS teaches the model where a text stops, which is what generate stops on (Chapter 8).

The biggest single improvement in this project came from the tokenizer (docs/RESULTS.md §7). 4.2 RMSNorm: keep the numbers in range

As a token's vector passes through block after block, each block adds to it. Without control, those numbers drift larger or smaller layer by layer, and training becomes unstable. A normalisation layer rescales each vector to a standard size before a block reads it.

AnuLM uses RMSNorm: divide the vector by its root-mean-square, then multiply each of its D numbers by a learned gain. It is LayerNorm without subtracting the mean and without a bias: cheaper, and in practice just as good.

# build/solutions/ch04.py, RMSNorm (identical to model.py's)
def __init__(self, dim, eps=1e-6):
    self.weight = nn.Parameter(torch.ones(dim))    # gain starts at 1: the identity scale
    self.eps = eps

def forward(self, x):
    dtype = x.dtype
    x = x.float()                                    # statistics in float32, whatever x is
    x = x * torch.rsqrt(x.pow(2).mean(-1, keepdim=True) + self.eps)
    return x.to(dtype) * self.weight

Two lines look like housekeeping and aren't. x.float() computes the mean of squares in 32-bit precision even when training runs in bfloat16, where it would quietly lose accuracy. And eps sits inside the square root, so a vector of near-zeros is divided by about 0.001 instead of by nearly nothing.

4.3 SwiGLU: the MLP

After a token has gathered information (attention, Chapter 6), the MLP processes it on its own. AnuLM's MLP is SwiGLU: it expands the vector from D to I numbers twice in parallel, lets one copy gate the other, and projects back down to D.

# build/solutions/ch04.py, SwiGLU (identical to model.py's)
self.gate_proj = nn.Linear(hidden_size, intermediate_size, bias=False)
self.up_proj   = nn.Linear(hidden_size, intermediate_size, bias=False)
self.down_proj = nn.Linear(intermediate_size, hidden_size, bias=False)

def forward(self, x):
    return self.down_proj(F.silu(self.gate_proj(x)) * self.up_proj(x))

That is 3 · D · I weights and no biases. In AnuLM, layer 0 has one dense SwiGLU like this; every later layer replaces it with a set of smaller ones, the experts of Chapter 7. Each expert is exactly this module.

4.4 The residual block

A block never replaces the vector it is given. It computes something from a normalised copy and adds the result back:

# build/solutions/ch04.py, MLPBlock
def forward(self, x):
    return x + self.mlp(self.post_attention_layernorm(x))

This is the pre-norm residual design. The original vector always survives unchanged along the x + path, so information and gradients pass straight through many blocks, and each block only has to learn a correction. The normalisation sits on the branch, not on the main path.

Note

The name post_attention_layernorm will make sense in Chapter 6, when attention is added in front of the MLP with its own input_layernorm.

4.5 Embeddings, the head, and the starting point

Embeddings turn each token id into D numbers: a table of vocab_size × D learned values (embed_tokens). At the top, after a final RMSNorm, the output head (lm_head) turns D numbers back into one score per token. AnuLM keeps these two tables separate (untied), as Sarvam's models do; tying them saves V × D parameters.

How the weights start matters. model.py draws every weight from a normal distribution with standard deviation 0.02, then redraws each down_proj, the layer that writes into the residual path, with 0.02 / √(2 · n_layer). Each block adds its output to the same running vector, so with many blocks those additions must start small or their sum starts large.

A correct starting model knows nothing, and should be equally unsure of every token: its loss on random text should be ln(vocab_size) = ln(259) = 5.557. Your skeleton, in the lab, starts at 5.562.

Positions: RoPE and YaRN

Attention, the subject of Chapter 6, compares every token with every earlier one, but on its own it has no idea how far apart they are. "Dog bites man" and "man bites dog" contain the same three words. This chapter builds how AnuLM tells them apart: rotary position embeddings (RoPE), and YaRN, the extension that lets a model read text longer than it was trained on. Neither does anything until attention exists, so this chapter's lab doesn't train. It measures, with model.py's own code: that RoPE depends only on distance, how much precision it needs, and what YaRN changes.

5.1 Why attention needs positions

In Chapter 4's skeleton every position saw only itself, so order never came up. Attention changes that: a token's query is compared with the keys of earlier tokens, and the result decides what it pays attention to. That comparison is a dot product, and a dot product doesn't know where the two vectors came from.

There are two ways to give it positions. You can add a learned vector for each position to the embeddings, as Chapter 1's tiny transformer did. Or you can rotate each query and key by an angle that grows with its position, so the dot product itself becomes position-aware. AnuLM, like Sarvam's models and most current LLMs, rotates.

5.2 Rotary embeddings: turn every pair by its position

RoPE splits each query and key into pairs of numbers. It treats each pair as a 2-D vector, and turns it by an angle: position × that pair's frequency.

The frequencies run from fast to slow. In a 64-dimension head there are 32 pairs. Pair 0 turns a full radian per position, and the slowest pair barely moves across a whole document. Together they work like the hands of a clock: some tell you the second, others the hour.

The rotation itself is two lines:

# build/solutions/ch05.py (identical to model.py's)
def rotate_half(x):
    x1, x2 = x[..., : x.shape[-1] // 2], x[..., x.shape[-1] // 2:]
    return torch.cat((-x2, x1), dim=-1)

def apply_rope(q, k, cos, sin):
    cos, sin = cos[None, None], sin[None, None]          # broadcast over batch and heads
    return q * cos + rotate_half(q) * sin, k * cos + rotate_half(k) * sin

q cos + rotate_half(q) sin is the 2-D rotation formula, applied to every pair at once. Which numbers form a pair is a convention. AnuLM pairs dimension i with i + 32 (the "split-halves" layout, from GPT-NeoX). Sarvam's 105B checkpoint pairs neighbours (i with i + 1). Both are correct; mixing them is not.

5.3 Why it works: the angles subtract

When a query at position i meets a key at position j, both have been turned. In a dot product of two rotated vectors, only the difference of their angles survives. So q·k depends on i − j, the distance, and not on where in the text the pair sits. The lab measures it:

The cos and sin values come from a small table, built once and shared by every layer:

# build/solutions/ch05.py, Rotary.forward
t = torch.arange(n, device=device, dtype=torch.float32)        # angles in float32, always
freqs = torch.outer(t, self.inv_freq.to(device).float())        # position x frequency
emb = torch.cat((freqs, freqs), dim=-1)                          # the split-halves layout
self.cos_cached = (emb.cos() * self.table_mscale).to(dtype)
self.sin_cached = (emb.sin() * self.table_mscale).to(dtype)

Two details matter. The table is indexed by absolute position, with a start offset, because in Chapter 6 the model generates one token at a time and asks for, say, position 700 alone. And the angles are computed in float32 whatever precision the model runs in. The lab shows why:

This is a real bug from this project. Casting the whole model to bfloat16 with model.to(torch.bfloat16) also cast the rotary frequencies. With the 400M model's settings, angles were off by 0.19 radians at position 200, and by 0.94 radians at position 1,000, the end of its context: tokens near the end of a long prompt were placed somewhere else entirely. The demo app now rebuilds the frequencies in float32 after casting.

5.4 Past the trained length: YaRN

A model trained on 256-token windows has never seen the angles that slow pairs reach at position 1,000. Some pairs complete many turns within 256 positions, so every angle is familiar. Others never complete one turn, and beyond the trained length they reach angles the model has never seen.

YaRN fixes the slow pairs and leaves the fast ones alone. Pairs that turn many times keep their frequency; pairs that never complete a turn are slowed by the extension factor, so position 1,000 lands on an angle position 250 used to have; the pairs in between are ramped smoothly. With a 4× extension of a 256-position context, 64 dimensions and theta 1e4, the lab finds 1 pair kept, 19 slowed 4×, and 12 on the ramp.

YaRN has a second half that is easy to miss: a temperature. Slowing the pairs makes attention scores slightly flatter, so YaRN multiplies the attention logits by mscale², where mscale = 0.1 · ln(factor) + 1. At 4× that is 1.1386² = 1.2965. Rotary computes it as attn_mscale; the attention layer in Chapter 6 must use it.

Chapter 4's skeleton stalled at the bigram table, 2.48, because every position could see only itself. This chapter gives it the ability to look back: attention. Along the way you'll meet the most dangerous bug in this book: a model that can see the future.

6.1 What attention does

At every position, attention asks: which earlier positions matter here, and what should I take from them? Each position produces three vectors from its current representation:

  • a query q: what this position is looking for;
  • a key k: what this position offers to others looking;
  • a value v: what it hands over if chosen.

The query is compared with every earlier key by a dot product, scaled down by √(head dimension) so the numbers stay moderate. A softmax turns the scores into weights that sum to 1, and the output is the weighted sum of the values. PyTorch does all of it in one call:

y = F.scaled_dot_product_attention(q, k, v, attn_mask=mask, is_causal=..., scale=self.scale)

Models run several of these side by side, heads, each with its own projections, so each can look for something different. In the lab, one head learns to look almost entirely at the previous byte; you'll see it at the end of the chapter.

6.2 The causal mask: never look ahead

A language model is trained to predict the next token. If position 5 could attend to position 6, it could simply read the answer, and training would reward it for doing so. The causal mask forbids it: a query may only attend to keys at its own position or earlier.

# build/solutions/ch06.py (identical to model.py's _attn_mask)
def attn_mask(S, T, start, window, device):
    if window is None and (start == 0 or S == 1):
        return None                                  # is_causal (or no mask) is enough, and faster
    q_pos = torch.arange(start, start + S, device=device)[:, None]
    k_pos = torch.arange(T, device=device)[None, :]
    mask = k_pos <= q_pos                            # never a key after the query
    if window is not None:
        mask &= k_pos > q_pos - window               # nor one window or more back
    return mask

Three cases need care.

  • Training (start == 0): PyTorch's built-in is_causal=True draws exactly the right triangle and uses a faster kernel, so the function returns None.
  • Decoding against a cache (Section 6.5): the queries are new tokens at positions 5, 6, 7, but the keys include the 5 cached ones. is_causal always draws its triangle from the top-left corner, so it would hide keys these queries must see (red in the figure). An explicit mask is needed.
  • A sliding window also hides keys that are too far back. The deployed 400M model uses a 256-token window on its first 10 of 20 layers; the other 10 see everything.

A leaking mask is the worst bug in this book. The model trains beautifully, because it is reading the answers, and the loss it reports means nothing. Nothing in the training curve will warn you. Only a check will.

6.3 Grouped-query attention

AnuLM uses grouped-query attention (GQA): many query heads, fewer key and value heads, each key/value head shared by a group of query heads. The 400M model has 16 query heads sharing 4 key/value heads.

# build/solutions/ch06.py, GQAttention.forward (identical to model.py's)
qkv = self.query_key_value(x).view(B, S, self.n_head + 2 * self.n_kv_head, self.head_dim)
q, k, v = qkv.split([self.n_head, self.n_kv_head, self.n_kv_head], dim=-2)
q, k, v = q.transpose(1, 2), k.transpose(1, 2), v.transpose(1, 2)   # (B, heads, S, Dh)
if self.use_qk_norm:                                    # normalise, THEN rotate
    q, k = self.query_layernorm(q), self.key_layernorm(k)
q, k = apply_rope(q, k, cos, sin)                       # Chapter 5
...                                                     # the cache, Section 6.5
k = k.repeat_interleave(self.n_rep, dim=1)              # each kv head serves n_rep query heads
v = v.repeat_interleave(self.n_rep, dim=1)
y = F.scaled_dot_product_attention(q, k, v, attn_mask=mask,
                                   is_causal=(mask is None and S > 1), scale=self.scale)
return self.dense(y.transpose(1, 2).reshape(B, S, -1))

Four details, each a place for a silent bug:

  • One fused projection makes q, k and v together, as Sarvam's 30B does.
  • QK-norm (an RMSNorm on each query and key head) keeps the attention scores from growing too large. It must come before RoPE. We measured what happens if it comes after: with the norm's gains at their starting value of 1, the two orders agree to 0.0000005, because a rotation doesn't change a vector's length. Once training moves the gains, outputs differ by up to 0.99. So the bug is invisible at the start and only grows as the model learns.
  • repeat_interleave, not repeat: query heads 0–3 share key head 0. repeat would give query head 1 key head 1's values instead, still a working model, just not the one any checkpoint was trained as.
  • The scale is 1/√(head dim), times YaRN's temperature from Chapter 5.

6.4 The full block

Chapter 4's block had only the MLP. The real one writes into the residual twice: once from attention, once from the MLP, each reading its own normalised copy.

x = x + self.attn(self.input_layernorm(x), cos, sin, cache=cache, start=start, window=self.window)
return x + self.mlp(self.post_attention_layernorm(x))

This is why model.py scales both dense (attention's output) and down_proj at initialisation by 1/√(2 · n_layer): two writes per layer.

6.5 Generating fast: the KV cache

To generate, the model predicts a token, appends it, and predicts again. Done naively, every step re-reads the whole text. But the keys and values of earlier tokens never change: the causal mask means they never see later tokens. So keep them. With a KV cache, the prompt is read once, and each later step feeds only the newest token, attending to the cached keys and values.

if cache is not None:
    if "k" in cache:
        k = torch.cat([cache["k"], k], dim=2)        # earlier keys, then the new one
        v = torch.cat([cache["v"], v], dim=2)
    cache["k"], cache["v"] = k, v                    # the n_kv_head heads, not their copies

Two things must be right. The new token's rotary angle must be for its real position, which is what Chapter 5's start offset is for. And the cache must hold the shared key/value heads, not their repeated copies, because that is the whole memory saving of GQA. At the 400M model's sizes, a token's cache costs:

Mixture of experts

A bigger model learns more, but every parameter normally costs compute on every token. A mixture of experts (MoE) breaks that link. It replaces one MLP with many smaller ones, the experts, and a router that sends each token to only a few of them. The model gets more parameters while each token does about the same work. This chapter builds AnuLM's router, its experts, and the rule that keeps the experts evenly used, all without an extra loss. At the end, your model is no longer like model.py's: your weights load into it and give the same outputs, digit for digit.

7.1 More parameters, the same work

In AnuLM, every layer after the first replaces its MLP with:

  • routed experts: 16 small SwiGLU MLPs in the 30b preset, each an eighth of the dense MLP's width (96 against 768); the router picks 2 per token;
  • a shared expert, one more SwiGLU that every token goes through, outside the routing.

So the 30b preset has 17,440,384 parameters, but any one token uses 6,602,368 of them: the experts it wasn't routed to do no work for it. That ratio is the point of the design. Sarvam's real models push it much further, with 128 experts.

7.2 The router

The router scores every expert for every token, and keeps the top k:

# build/solutions/ch07.py, Router._gate (identical to model.py's)
logits = F.linear(x, self.weight.float())             # (tokens, experts)
scores = torch.sigmoid(logits)                         # each expert scored on its own
choice = scores + self.expert_bias[None, :]            # the balancing bias steers the choice ...
idx = choice.topk(self.top_k, dim=-1)[1]               # the k winners
w = scores.gather(1, idx)                              # ... but the weights come from the plain scores
w = w / (w.sum(-1, keepdim=True) + 1e-20) * self.routed_scaling_factor

Three choices here are DeepSeek-V3's, which Sarvam's models follow.

  • Sigmoid, not softmax. Each expert is scored independently, so one expert winning doesn't push the others down.
  • The bias picks, but never weights. expert_bias, introduced in Section 7.5, is added only when choosing. The winners are then weighted by their unbiased scores, normalised to sum to 1 and scaled by 2.5.
  • Group-limited routing (the 105b preset): experts are split into groups, and a token may only use experts from its best few groups. On large machines, each group lives on one device, so this limits traffic.

The router runs in float32, even when the rest of the model runs in bfloat16. Picking the top k is a discrete choice, and rounding can flip it. The lab-notebook box at the end of this chapter tells how we found that out.

7.3 The MoE layer

Once every token has its k experts, each expert runs once, on all the tokens sent to it, and the outputs are put back, weighted:

# build/solutions/ch07.py, MoE.forward (model.py's "sparse" path)
flat_expert = idx.reshape(-1)                                   # one entry per (token, slot)
token_of_slot = torch.arange(N).repeat_interleave(self.top_k)   # which token each slot belongs to
out = x_flat.new_zeros(N * self.top_k, D)
for e in range(self.num_experts):
    sel = (flat_expert == e).nonzero(as_tuple=True)[0]          # the slots routed to expert e
    if sel.numel():
        out[sel] = self.experts[e](x_flat[token_of_slot[sel]])
y = (out.view(N, self.top_k, D) * w.unsqueeze(-1)).sum(1)       # weighted sum per token
y = y + self.shared_expert(x)                                   # every token, outside routing

model.py has two more ways to do the same arithmetic. dense runs every expert on every token and keeps the chosen outputs: wasteful, but its shapes never change, so torch.compile handles it in one piece. grouped sorts tokens by expert and runs all experts in a single grouped matrix multiply, which is 1.48× faster on a GPU (docs/RESULTS.md §4). All three give the same outputs; the tests hold them to it.

7.5 Keeping the experts busy, without a loss

Left alone, a router tends to find a few favourite experts and send them most of the traffic. The others get few tokens, learn little, and get chosen even less. The classic fix adds a balancing loss to training, which also pulls the model away from what it is trying to learn.

AnuLM uses DeepSeek-V3's alternative: a bias with no gradient at all. Each router counts how many tokens every expert received. After each optimizer step, each expert's bias moves by a fixed small step: down if it was busier than average, up if it was quieter.

# build/solutions/ch07.py, MoELM.update_expert_biases
load, mean = m.load_counts, m.load_counts.mean()
m.expert_bias += self.bias_update_rate * torch.sign(mean - load)   # busy: down; idle: up
load.zero_()

Because the bias only affects which experts are picked, never how their outputs are weighted, balancing never touches the gradient the model learns from. And because expert_bias is a buffer, not a parameter, the optimizer never sees it.

In the lab, both runs start badly unbalanced: the busiest expert gets about 2.5× its fair share. With the bias rule, imbalance falls to 1.04×; without it, the router settles at 1.83×.

Our records describe how the rule behaves (docs/RESULTS.md §5): imbalance rises before it falls (peaks of 5–8× in our runs), because the bias moves slowly at first. Because sign() takes a full step however small the error, it never settles exactly, and oscillates around balance instead.

8.1 Generating text

Chapter 6 gave you a minimal generate. The real one, model.py's, adds four controls, applied to the last position's logits in a fixed order:

# build/solutions/ch08.py, MoELM.generate (identical to model.py's)
if repetition_penalty != 1.0:                        # tokens already used: less likely again
    seen = logits.gather(1, idx)
    seen = torch.where(seen > 0, seen / repetition_penalty, seen * repetition_penalty)
    logits = logits.scatter(1, idx, seen)
logits = logits / max(temperature, 1e-5)             # below 1 sharper, above 1 flatter
if top_k is not None:                                # only the k most likely survive
    v, _ = torch.topk(logits, min(top_k, logits.size(-1)))
    logits[logits < v[:, [-1]]] = -float("inf")
nxt = torch.multinomial(F.softmax(logits, dim=-1), num_samples=1)

The repetition penalty has a subtlety. A positive logit is divided by the penalty, but a negative one is multiplied. Dividing a negative logit would bring it closer to zero and make the token more likely. Two more details matter in practice. With eos_id, a row that has finished keeps receiving the end token, so a batch stays rectangular, and generation stops when every row is done. And when the KV cache reaches block_size, it is rebuilt from the last block_size tokens, which gives exactly what re-reading them would.

The check holds you to model.py token for token: same weights, same seed, same text, including past the end of the context.

8.2 The learning-rate schedule

The learning rate is the size of each step. Every run warms it up from near zero (the first steps' gradients are wild) and lowers it near the end (small steps settle the model into a good spot). AnuLM's train.py offers two shapes:

  • cosine: after warmup, the rate falls along half a cosine wave to a minimum at the last step;
  • warmup-stable-decay (WSD): after warmup, the rate stays flat at its peak, then falls in a straight line over the last part of the run.
# build/solutions/ch08.py, lr_at (identical to train.py's)
if step < warmup:
    return lr * (step + 1) / max(warmup, 1)
if schedule == "wsd":
    decay_start = int(steps * (1 - decay_frac))
    if step < decay_start:
        return lr
    return lr + (min_lr - lr) * min((step - decay_start) / max(steps - decay_start, 1), 1.0)
progress = min((step - warmup) / max(steps - warmup, 1), 1.0)
return min_lr + 0.5 * (lr - min_lr) * (1 + math.cos(math.pi * progress))

WSD has a practical advantage, which the lab shows: while the rate is flat, you can stop the run, extend it, or decay a copy at any point, without disturbing the main run.

8.3 The optimizer

Every AnuLM run uses AdamW with three choices that matter:

# build/solutions/ch08.py, make_optimizer (train.py's groups)
decay    = [p for p in model.parameters() if p.requires_grad and p.dim() >= 2]
no_decay = [p for p in model.parameters() if p.requires_grad and p.dim() < 2]
torch.optim.AdamW([{"params": decay, "weight_decay": 0.1},
                   {"params": no_decay, "weight_decay": 0.0}],
                  lr=lr, betas=(0.9, 0.95), eps=1e-8)

Weight decay gently shrinks weights towards zero every step, which keeps them from growing without need. It belongs on the big matrices, never on the RMSNorm gains: decaying those would drag every normalisation layer towards zero for the whole run. betas (0.9, 0.95), rather than PyTorch's default 0.999, let the optimizer's running estimates adapt faster, which large-model training has found more stable. And the experts' balancing bias is not here at all: it is a buffer, not a parameter (Chapter 7).

train.py also offers Muon, which orthogonalises each matrix's update. In our small-scale comparison (docs/RESULTS.md §32), batched Muon was the largest single gain we found, −0.371 in loss at the same 25M tokens.

8.4 Gradient accumulation and the step

A big batch gives a cleaner gradient, but may not fit in memory. Gradient accumulation splits it into micro-batches, adds up their gradients, and only then takes one step. To get the mean loss's gradient, each micro-batch's loss is divided by their number:

# build/solutions/ch08.py
def accumulate(model, batches):
    model.zero_grad(set_to_none=True)
    for x, y in batches:
        _, loss = model(x, y)
        (loss / len(batches)).backward()          # each micro-batch's share of the mean

def train_step(model, opt, batches, lr, clip=1.0):
    ...
    loss = accumulate(model, batches)
    torch.nn.utils.clip_grad_norm_(model.parameters(), clip)    # no step larger than this
    opt.step()
    model.update_expert_biases()                  # after the step, never part of the loss

What if you forget the / len(batches)? We measured it. With 4 micro-batches, the gradient is 4× too large (norm 5.39 against 1.35). But after clipping and one AdamW step, the weights differed by 0.000000015, nothing at all. AdamW divides each gradient by its own running size, and clipping caps the norm, so a constant factor nearly disappears. The bug is real (it breaks plain SGD, the logged loss, and any clipping threshold you tuned), yet checking the weights would never find it. The check compares gradients.

8.5 Checkpoints you can resume from

A run that dies on day four must not start over. A resume point has to hold everything that determines what happens next:

  • the weights, and the buffers: the experts' balancing biases aren't parameters, but they are part of the model;
  • the optimizer's state: AdamW's running averages, one pair per weight;
  • the step, so the schedule continues where it was;
  • the data order: the random generator's state, so the next batches are the ones the uninterrupted run would have seen.

And it must be written so that a crash while saving can't destroy it:

# build/solutions/ch08.py, save_checkpoint
tmp = Path(str(path) + ".tmp")
torch.save({"model": model.state_dict(), "opt": opt.state_dict(), "step": step, **extra}, tmp)
os.replace(tmp, path)                             # one indivisible swap

Teach it to answer

A pre-trained model continues text. Ask it a question and it writes whatever would most likely follow those words: more questions, a story, an article. Supervised fine-tuning (SFT) shows it many questions, each followed by an answer, until answering is what follows. The code is short: format each pair, pack the pairs into rows, and keep the loss off the question. Every bug in it still trains, so you won't see one in the loss curve. The model just learns a little less of what you meant.

9.1 One pair, as ids

make_qa.py has one template per language. The English one is:

Question: {q}
Answer:

The answer follows after one space, then the end-of-text id:

# build/solutions/ch09.py, pair_ids (identical to finetune.py's _pair_ids)
return encode(template.format(q=question)), encode(" " + answer) + [eos]

Two details matter.

The space goes with the answer. A BPE tokenizer splits text into chunks that start with their space (Chapter 3: " the" is one token). Written out in full, "Answer: New Delhi" contains the token " New", not "New". Encode the answer without its space, and every fine-tuning example starts the answer with a token the model will never meet when it reads the prompt and answer as one text, which is exactly how it will meet them when it is used.

The answer ends with EOS. The end token is the only thing that teaches the model to stop. Leave it out and the model answers, then keeps going: another question, another answer, until it hits the length limit.

9.2 Pack the pairs; grade only the answers

Pairs are short and rows are long, so several pairs share one row, which wastes no compute on padding. Every position is still trained to predict the next id, but the targets for the question's ids are set to −1, which the loss ignores (ignore_index=-1, Chapter 4).

# build/solutions/ch09.py, pack (identical to finetune.py's)
for p, a in pairs:
    ex = p + a
    if len(ex) > block_size:
        continue                                   # too long for any row: dropped, never cut
    if len(ids) + len(ex) > L:
        flush()                                    # doesn't fit: start a new row
        ids, lab = [], []
    ids = ids + ex
    lab = lab + [-1] * len(p) + list(a)            # the prompt is read, never graded
...
return x[:, :-1].contiguous(), y[:, 1:].contiguous()   # position t predicts id t + 1

Rows are block_size + 1 ids long, so that the shift by one (x is the row without its last id, y the labels without their first) leaves block_size predictions per row. The last prompt position, the one reading "Answer:", is graded on the answer's first id, because that is the prediction the model will have to make when it is used.

A pair is never split across two rows. Its second half, alone at the start of a row, would be an answer with no question, and the model would learn to produce answers to questions it was never asked.

LoRA and QLoRA: fine-tuning on a budget

Chapter 9 changed every weight of the model. This chapter changes almost none of them. LoRA freezes the model and trains a thin correction beside a few of its layers. QLoRA does the same with the frozen weights squeezed into 4 bits. You will write both in course/build/post.py, on the expert model you built in Part II, and teach it a language it has never seen, Hindi. Along the way you will hit two problems that tutorials on dense models never show: a language whose bytes the model never learned, and expert biases that keep moving while everything else is frozen.

10.1 Why not just fine-tune everything?

A full fine-tune keeps training every weight, exactly as pre-training did. It is the simplest option and usually the best one. Its problem is memory. For every weight, the GPU must hold the weight itself, its gradient (which way it should move), and two running averages that the AdamW optimizer keeps: 4 + 4 + 8 = 16 bytes per weight, before counting the text being processed.

For the 398M AnuLM model that is 6.4 GB, which fits a 16 GB gaming card. For a 7-billion-parameter model it is 112 GB, which fits no consumer GPU at all. LoRA and QLoRA exist to close that gap.

10.2 LoRA: a thin correction beside a frozen weight

LoRA (low-rank adaptation) freezes the original weight matrix W and trains a small correction beside it. The correction is not a full matrix the size of W. It is the product of two thin ones, B and A:

The number r, the rank, sets how thin they are. Your layer is lora.py's, name for name, so the checks can load one into the other:

# build/solutions/ch10.py, LoRALinear (identical to lora.py's)
def __init__(self, base, r=16, alpha=32.0):
    self.base = base                                        # frozen: requires_grad False
    self.scale = alpha / r
    self.lora_a = nn.Parameter(torch.empty(r, base.in_features))
    self.lora_b = nn.Parameter(torch.zeros(base.out_features, r))   # zero: start as the base
    nn.init.kaiming_uniform_(self.lora_a, a=math.sqrt(5))

def forward(self, x):
    return self.base(x) + ((x @ self.lora_a.t()) @ self.lora_b.t()) * self.scale

Three details matter more than they look.

  • B starts at zero. At step 0 the correction is exactly nothing, so the model starts as the base model and can't begin worse than it. (A can't also be zero, or neither would ever get a gradient.)
  • The scale is alpha / r. Doubling the rank doubles the number of terms in the correction; dividing by r keeps its size, and so the right learning rate, about the same.
  • Only A and B get gradients and optimizer state. That is where the memory saving comes from: the 16 bytes per weight from §10.1 now apply only to the adapter's numbers.

apply_lora freezes every parameter in the model, then wraps each Linear whose name ends with a target. lora.py's default targets are the attention projections, attn.query_key_value and attn.dense. On your Chapter 8 model that is 8 layers, and at r = 16, 40,960 trainable numbers, 4% of the model. On the 398M model it is 0.4%.

After training, merge_lora folds each correction into its weight, W + (alpha / r) · B A, and puts the plain Linear back. The merged model is an ordinary checkpoint, and it costs nothing extra to run. In the lab, merging changed no logit by more than 0.00003.

10.3 QLoRA: keep the frozen part in 4 bits

LoRA still keeps the frozen weights in full 32-bit precision, which is the largest item on the memory bill. QLoRA notices that frozen weights only have to be read, never updated, and stores them in 4 bits: one-eighth of the memory.

Four bits allow only 16 different values. The trick is choosing which 16. Trained weights are spread like a bell curve, crowded near zero, so QLoRA's NormalFloat-4 (NF4) format puts its 16 levels where the weights are:

Weights are handled in blocks of 64. Each block is divided by its largest absolute value, so it fits between −1 and 1. Each weight is then replaced by the code of its nearest level, and two 4-bit codes are packed into each byte:

# build/solutions/ch10.py
def nf4_quantize(w):
    flat = w.detach().float().reshape(-1, BLOCK)
    absmax = flat.abs().max(dim=1, keepdim=True).values.clamp_min(1e-12)   # one scale per block
    codes = torch.bucketize(flat / absmax, (NF4[1:] + NF4[:-1]) / 2).to(torch.uint8).reshape(-1)
    return (codes[0::2] << 4) | codes[1::2], absmax.squeeze(1)              # two codes per byte

def nf4_dequantize(packed, absmax, shape):
    codes = torch.stack([packed >> 4, packed & 15], dim=1).reshape(-1).long()
    return (NF4[codes].reshape(-1, BLOCK) * absmax[:, None]).reshape(shape)

bucketize against the midpoints between levels gives each weight its nearest level. An NF4Linear keeps only the packed codes and the scales, as buffers, with no parameters at all, and rebuilds an approximate weight in every forward pass. apply_lora(..., quantize=True) wraps it in a LoRALinear exactly as before. Gradients flow through the rebuilt weight into the adapters.

How much does squeezing cost? In the lab, storing the attention weights in NF4 moved the model's Shakespeare loss from 1.509 to 1.512.

Note

The repository has no QLoRA: lora.py's docstring explains that at 398M, 4-bit storage would save about 1.2 GB, which wasn't worth a dependency on bitsandbytes. This chapter's NF4 is new code. Production QLoRA adds double quantization, which compresses the per-block scales too, and paged optimizers, which spill optimizer state to CPU memory during spikes.

Preference tuning with DPO

Supervised fine-tuning shows the model a good answer. It never shows it a bad one. Preference tuning trains on pairs of answers to the same prompt, one preferred (chosen) and one not (rejected), and teaches the model to tell them apart. DPO, Direct Preference Optimization (Rafailov et al., 2023), is the simplest way to do it: no reward model, no sampling during training, just one loss on log-probabilities.

DPO is new code: AnuLM's models were never preference-tuned, so there is no dpo.py in the repository to match. This chapter's lab is the first DPO run on this project. It didn't go the way the tutorials suggest, and the checks and the measurements show why.

11.1 Where preference pairs come from

A pair needs a prompt and two answers, one better than the other. People can rate answers, a stronger model can, or a program can, when correctness can be checked. The lab uses the last kind, because it needs nothing outside your machine. Chapter 9's model answers every training sum four times, sampling at temperature 1, and a line of Python checks each answer:

Question: what is 44 plus 56?
Answer: 100      chosen
Answer: 110      rejected

Out of 24,000 sampled answers, 90.9% were right. 1,058 of the 6,000 questions got at least one right and one wrong answer, and each of those gives a pair. These are the questions the model is unsure about, which is where a pair can teach it something.

11.2 The log-probability of an answer

Everything DPO needs is one number per answer: the log-probability the model gives it, the sum over its ids of log p(id | everything before it). It has to count the answer's ids, and only those:

# build/solutions/ch11.py, answer_logprobs
mask[i, len(p) - 1: len(p) - 1 + len(a)] = 1.0       # position t predicts id t + 1
logits, _ = model(ids[:, :-1])
logp = F.log_softmax(logits.float(), dim=-1).gather(-1, ids[:, 1:, None]).squeeze(-1)
return (logp * mask).sum(-1)

It is Chapter 9's mask again: the prediction of the answer's first id is made at the prompt's last position. Pairs in a batch have different lengths, so rows are padded on the right. The model is causal, so padding after an answer can't change the positions before it, and the mask never counts it.

11.3 The loss

DPO compares two models: the policy, which trains, and the reference, a frozen copy of where the policy started. For each answer it asks how much more likely the policy makes it than the reference did:

# build/solutions/ch11.py, dpo_loss
margin = beta * ((pol_chosen - ref_chosen.detach()) - (pol_rejected - ref_rejected.detach()))
return -F.logsigmoid(margin).mean(), margin.detach()

At the first step the policy is the reference, every margin is 0, and the loss is −log sigmoid(0) = ln 2 = 0.693. The gradient isn't zero, though: it pushes the chosen answer up and the rejected one down from the first step. beta sets how strongly the margin counts: a small beta needs a large change in log-probabilities before the loss is satisfied.

dpo_step puts it together: the reference's log-probabilities under torch.no_grad(), the policy's with gradients, the loss, clipping, the optimizer step, and then, because this is your expert model, the balancer (Chapter 8). It also takes an sft_weight, which the lab will show you need.

Decisions and lookup

Not every job wants prose. Software often needs a decision: which queue a message goes to, which intent it is, whether to answer or hand it to a person. And a small model can't remember many facts, but it can read them if something finds the right page first. This chapter builds both, the way AnuLM does: Decide, which scores a list of options in one pass and says how sure it is, and BM25, the search behind rag.py.

12.1 Decide: one pass, a probability for every option

decide.py puts the message and every option's name in one sequence, then reads the model's hidden state at the last token of each option's name. Because the model is causal, that position has read the message and that option. A one-number linear head scores each of those states, and a softmax over the scores gives a probability for every option.

# build/solutions/ch12.py, encode_options (identical to decide.py's encode)
ids = [bos] + encode(f"Message: {text.strip()}\nWhich of these does it ask for?\nOptions:")
pos = []
for o in options:
    ids += encode(f"\n- {readable(o)}")          # 'card_arrival' -> 'card arrival'
    pos.append(len(ids) - 1)                     # where this option's score is read
# build/solutions/ch12.py, Decider.forward
h = final_hidden(self.model, idx)                                   # (B, S, hidden)
g = h.gather(1, pos[..., None].expand(-1, -1, h.shape[-1]))         # one state per option
logits = self.head(g).squeeze(-1).float()
return logits if mask is None else logits.masked_fill(~mask, float("-inf"))

Three details matter. The answer can only be one of the options, never a misspelling or an invention. The options are shuffled for every training example, so the head learns to read names, not positions, and the same model takes any list. And when examples in a batch have different numbers of options, the missing ones are set to −∞, so they get probability 0.

12.2 Calibration: 0.9 should mean right nine times in ten

A probability is only useful if it means what it says. Calibration compares confidence with accuracy: of all the answers given with confidence around 0.9, about 90% should be right. The standard summary is the expected calibration error (ECE): sort answers into bins by confidence and add up, weighted by each bin's size, how far each bin's confidence is from its accuracy.

Models trained with cross-entropy are usually overconfident. The fix (Guo et al., 2017) is one number, a temperature T: divide every logit by T before the softmax. T > 1 softens the probabilities, and it never changes which option wins. fit_temperature tries T = 0.30, 0.35, …, 5.00 on held-out messages and keeps the one with the lowest cross-entropy.

With calibrated confidence, Decide can choose when to answer. Set a threshold and hand everything below it to a person: you trade coverage for accuracy, and you know the rate in advance.

12.3 Lookup: BM25

Retrieval-augmented generation (RAG) finds passages that might hold the answer, then has the model read them. rag.py's finder is BM25, the classic scoring function of search engines, written from scratch. For each query word, each passage scores

idf × tf × (k₁ + 1) / (tf + k₁ × (1 − b + b × length / average length))

  • tf is how often the word appears in the passage. Its effect saturates: the tenth "India" counts for less than the first. k₁ = 1.2 sets how fast.
  • idf = log(1 + (N − df + 0.5) / (df + 0.5)) is high for words in few passages and near zero for words in all of them, so "the" counts for almost nothing. (Without the 1 +, it goes negative for very common words.)
  • b = 0.75 normalises for length: a long passage contains more words by chance, so each match counts for a little less.

Each distinct query word counts once. And the words have to be the right words:

# build/solutions/ch12.py (identical to rag.py's)
WORD = re.compile(r"[0-9A-Za-zÀ-ɏऀ-ॿ]+")      # Devanagari vowel signs are word characters

Python's \w matches letters and digits, but not the Devanagari vowel signs (matras), which Unicode classes as marks. re.findall(r"\w+", "राजधानी") returns ['र', 'जध', 'न']: three fragments, none of them a word.

Hearing and seeing

A language model reads ids. To hear or see, it needs a way in for sound and pictures. AnuLM uses two. For speech it writes, it grows its vocabulary: every audio code gets an id, and the model learns to emit them like any other token. For pictures and speech it reads, a frozen encoder (SigLIP for images, Whisper for audio) turns the input into vectors, a small projector resizes them to the model's width, and they go in as embeddings with no ids at all. This chapter builds both on your model and asks the question every multimodal model should be asked: does it actually look?

13.1 New ids, new rows

speech_vocab.py appends 28,672 SNAC audio codes and five control tokens (<|speech|>, <|/speech|>, <|text|>, <|image|>, <|/image|>) to the vocabulary. Every id the model already had keeps its number and its row, so on text the grown model is exactly the model that went in.

Two decisions matter.

Grow both tables. AnuLM's output head is not tied to its embeddings. Grow only the embedding table and the model can read the new ids but never write them; grow only the head and the reverse. Either fails as a shape error minutes into training, or worse, doesn't fail at all.

Start the new rows where the old ones live. A fresh N(0, 0.02) row is far from the trained rows, and the first few hundred steps would be spent moving it there:

# build/solutions/ch13.py, grow_rows (identical to speech_vocab._grow)
mean = weight.mean(dim=0, keepdim=True)
std = weight.std().item()
noise = torch.randn(n_new, weight.shape[1], generator=gen, dtype=weight.dtype) * (std * 0.1)
return torch.cat([weight, mean.expand(n_new, -1) + noise], dim=0)

The bill is real. On the 400M model, 28,677 new ids at width 1,024 add 29.4M parameters to each table: 15% more parameters, but 34% more active ones, because embeddings are used by every token and the experts they join are not (speech_vocab.py's docstring).

13.2 Vectors in, with no ids

To feed pictures, the model needs a forward pass that starts from vectors. Yours is the same pass without the lookup:

# build/solutions/ch13.py, forward_embeds
x = embeds                                           # (B, S, hidden): no embed_tokens
cos, sin = model.rotary(x.shape[1], x.device, x.dtype)
for layer in model.layers:
    out = layer(x, cos, sin)
    x = out[0] if isinstance(out, tuple) else out    # an expert layer also returns its aux loss
logits = model.lm_head(model.norm(x))

Fed model.embed_tokens(ids), it must give exactly what model(ids) gives, and the checks hold it to that. Everything in this chapter goes through it.

13.3 The projector, and where the picture goes

SigLIP cuts a 224 × 224 picture into a 14 × 14 grid of patches and returns one 768-number vector per patch: 196 vectors. vision_encoder.py pools each 2 × 2 square of neighbours into one vector of 4 × 768 numbers, then a small network maps it to the model's width: Linear, GELU, Linear, LayerNorm.

The pooling has a trap. The 196 vectors arrive as a flat list, row by row. Pooling four consecutive vectors would join the right edge of one row of the picture with the left edge of the next. The squares have to be found in 2-D:

# build/solutions/ch13.py, ImageProjector.forward (identical to vision_encoder.py's)
x = patches.reshape(g, g, D)                                    # back to a grid
x = x.reshape(gp, self.pool, gp, self.pool, D).permute(0, 2, 1, 3, 4)
patches = x.reshape(gp * gp, D * self.pool * self.pool)         # one vector per square

build_caption then lays out one sequence: <|image|>, the 49 projected vectors, <|/image|>, and the caption. The targets are Chapter 9's: −1 everywhere except the caption's ids, each one position early. The picture is read, never graded.

13.4 How loud is a picture?

A LayerNorm with its default gain of 1 outputs vectors with norm √width: 11.3 for your model's 128, 32 for the 400M model's 1,024. A text token's embedding is much smaller: 0.29 here, 0.39 in AnuLM's chat model. So every picture vector arrives some 40 to 80 times louder than a word. omni_train.py's _match_scale shrinks the projector's final LayerNorm, gain and bias by one factor, so its output arrives at a word's size:

# build/solutions/ch13.py, match_scale (identical to omni_train's _match_scale)
target = text_embeddings.float().norm(dim=-1).mean()
now = (ln.weight.float().pow(2).sum() + ln.bias.float().pow(2).sum()).sqrt()
ln.weight.mul_(target / now)
ln.bias.mul_(target / now)

For a normalised input z, the expected squared norm of g × z + b is the sum of *g*² plus the sum of *b*², so one factor on both sets it. The factor stays learnable, and it is saved in the checkpoint, so inference needs nothing new.

One model for everything, and debugging it

Until AnuLM-Omni, every skill in this project was its own full copy of the model: a chat model, a reader, two speech models, a captioner and an image-question model. Copies like that can't share a GPU and can't be released as one thing. omni_train.py trains one decoder on all of it at once.

This chapter is about the code that does that, but mostly about what happened the first time it ran: a 100,000-batch run whose single number improved by 41% while the skill it was meant to keep got far worse. How the regression was hidden, how it was found, the wrong first theory, and the probes that found the real cause are the most useful things in this book that no tutorial teaches.

14.1 One model, many tasks

Every task's batch reaches the model as the same thing: input vectors, and targets with −1 on everything but the answer (Chapters 9 and 13). So one optimizer and one backbone serve all of them. What differs per task is small: how its inputs are built, and its share of the batches.

# build/solutions/ch14.py, pick_task (omni_train.py's draw)
w = np.asarray(shares, dtype=float)
return int(rng.choice(len(w), p=w / w.sum()))

Shares are a policy, not a fact about the data. experiments/omni_one.py gives Hindi speech 32% of the batches, because it is the weakest skill and has the most data, and chat 25%, although the model starts as a chat model and only has to keep chat. Why chat needed that much is the story of this chapter.

14.2 One number for seven tasks

To pick the best checkpoint, omni_train.py needs one number. Each task's held-out loss is divided by its value at step 0, and the ratios are averaged:

# build/solutions/ch14.py, score (omni_train.py's)
return float(np.mean([losses[k] / first[k] for k in losses]))

Dividing by the start keeps a task with a big loss (captions) from drowning out one with a small one (speech). The score starts at 1.0, and lower is better. Here is what it did on the first run:

The score fell from 1.0 to 0.587. Every new skill improved enormously: the intent classifier went from a held-out loss of 7.78 to 0.25. And chat, the skill the model started with, went from 3.27 to 5.39 in the first 10,000 batches and never came back. A mean of seven ratios has no way to say that one of them got worse while six got much better.

14.3 Finding the cause

The first theory was the projectors. Chapter 13 showed that a default LayerNorm makes picture and audio vectors about 80 times louder than a word's embedding. Perhaps the shared blocks retuned themselves to the loud inputs at the expense of text. _match_scale was written to test it, and an A/B of 3,000 batches each gave chat 4.97 without it and 4.95 with it. The theory was wrong.

So the probes took tasks away. If chat drifted when it trained alone, the other tasks weren't the cause.

Chat drifted even alone: 3.27 → 3.59 in 1,000 batches through omni_train.py, one batch a step. The same 1,000 batches summed four at a time (250 steps) kept it at 3.27. A fifth of the learning rate gave 3.35.

The cause was the steps themselves. AdamW moves every weight by roughly the learning rate on every step, whatever the batch held, because it divides the gradient by its own running size. A chat batch of 8 examples, or an intent batch with about 30 answer tokens, is a noisy estimate of where to go, and AdamW takes a full step in that direction anyway. A model that already sits in a good spot for chat gets knocked out of it by 100,000 noisy full-size steps. Summing several batches into one step averages the noise before the step is taken:

# build/solutions/ch14.py, omni_step
for _ in range(accum):
    x, y = draw()                       # any task
    _, loss = model(x, y)
    (loss / accum).backward()           # each batch's share of the mean
torch.nn.utils.clip_grad_norm_(model.parameters(), clip)    # once, on the sum
opt.step()
opt.zero_grad(set_to_none=True)
model.update_expert_biases()

With all seven tasks and eight batches a step, chat ended the same 3,000 batches at 3.55 instead of 4.97. Giving chat 25% of the batches brought it to 3.40, and 15% at half the learning rate to 3.37. The retrain uses all three levers together: ACCUM = 8, chat's share 0.25, and LR = 2.5e-5. That combination was never probed as a set, so its result will be the measurement.

14.4 Gates: a release decision that one number can't override

A score picks checkpoints. It must not decide releases. omni_one.py sets a gate for each task: how much it may lose against the separate model it replaces. If any gate fails, nothing is published, however good the mean.

# experiments/omni_one.py, GATES (part)
"chat_heldout_loss": ("<=", 3.30),     # chat_v3: 3.146 by omni_eval.py
"wer_en": ("<=", 9.0),                 # asr_en_v3: 7.1% on the same 100 clips
"intent_banking77": (">=", 80.0),      # the Decide adapter: 89.0%

Your gates matches it. A measurement that is missing fails its gate: a gate is a promise that something was measured. The Hindi speech gate is the mean of three test sets, because each set alone pulled the decision a different way: training on real speakers took Kathbath's error from 37.0% to 24.9% and MUCS's from 79.2% to 55.6%, while FLEURS got 3 points worse.

Key takeaways

  • One model can learn many tasks if every batch arrives in the same shape; shares of the batches are a policy you choose.
  • A single score averages away a regression: the first Omni run improved by 41% while chat went from 3.27 to 5.39.
  • Probe by taking things away. Chat drifted on its own, which ruled out the other tasks and the projectors, and pointed at the steps.
  • Many noisy one-batch AdamW steps knock a model out of a good spot. Summing batches into one step, a larger share, or a lower rate protects a skill, and the lab shows they can cost the new tasks.
  • Release on gates, one per task, and fail any measurement that wasn't made.

Shipping

A model on your disk helps one person. Shipping it means four more jobs: a file format other people can load safely, a statement of what the model is and what it may be used for, a measured decision about whether it is good enough, and something people can talk to. The bugs here are the ones your users find: a release that lost its projector, router biases rounded away, a model card that says "pass" for a measurement nobody made.

15.1 From a checkpoint to a release

A training checkpoint is a Python pickle: weights, buffers, the optimizer's moments, the step, and whatever else was saved, often three times the size of the weights. Loading a pickle can run code, so you should only ever open one you made yourself. A release is different. export_hf.py writes a folder of data only:

safetensors stores raw tensors and their names, and nothing that executes. The weights go in as bfloat16, half the size of float32, but not all of them:

# build/solutions/ch15.py, to_bf16 (identical to export_hf.py's)
if v.is_floating_point() and v.numel() >= 100_000:
    v = v.to(torch.bfloat16)

Big matrices lose little in bfloat16. Small tensors are cheap to keep exact and are often precision-sensitive: norm gains, and the experts' balancing biases, which are small numbers that decide routing by small differences (Chapter 7 measured 0.4% of routing choices flipping in bfloat16). Integer buffers, such as the experts' load counts, must never be converted.

15.2 A release has to keep everything

A model that hears or sees is more than a language model: the projector, a Decide head, LoRA adapters and their labels all live beside the backbone. tensor_groups finds every one of them, as every dict of tensors in the checkpoint other than the backbone's, and the export writes them to extras.safetensors. Forget one and the release still loads. It just can't see any more.

# build/solutions/ch15.py, tensor_groups (identical to export_hf.py's)
return {k: v for k, v in ck.items() if k not in CORE_KEYS and isinstance(v, dict) and v
        and all(torch.is_tensor(t) for t in v.values())}

Loading reverses it: every bfloat16 tensor is widened back to float32, every group returns under its own name, and the settings come from config.json. In the repository, model.load_checkpoint accepts such a folder anywhere a .pt path is accepted, so every script works on a release unchanged.

15.3 The release decision

Chapter 14's gates decide; the model card reports. release_report turns measurements and gates into the table a card carries, and its last line is the decision:

# build/solutions/ch15.py, release_report
for k, (op, thr) in rules.items():
    v = results.get(k, "-")
    lines.append(f"| {k} | {v} | {op} {thr} | {'yes' if gate_results.get(k) else '**no**'} |")
ok = all(gate_results.get(k) for k in rules)

A missing measurement prints "-" and fails. The report shows the value the gate actually judged, so when a gate computes a value (the Hindi mean), the report has to show that value too. Our first version of this lab printed "-" for the Hindi mean beside a "yes".

The card also carries the licence, and for a model the licence is decided by its data. docs/PUBLISHING.md §1 lists every AnuLM release with its licence and why: the coder is CC BY-NC-SA 4.0 because it was tuned on non-commercial, share-alike exercises; the translator is CC BY-NC 4.0, research only, because of Samanantar and the IIT Bombay corpus; AnuLM-Omni was built from commercially usable data only, so it can be CC BY-SA 4.0 with commercial use allowed. One set of weights inherits every training set's terms.
